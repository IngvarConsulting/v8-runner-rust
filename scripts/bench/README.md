# `scripts/bench`

Повторяемый стенд «раннер против Конфигуратора»: одна и та же правка в модулях проходит через
раннер и через исполнителей платформы без раннера, время и проверка того, что правка дошла
до базы, пишутся в JSONL, итог — таблица медиан.

Только Windows и установленная платформа 1С. Нужны Python 3.11+ (`tomllib`), `git` и, для голого
агента, `python -m pip install paramiko`.

## Файлы

| Файл | Что в нём |
| --- | --- |
| `bench.py` | Команды `list`, `setup`, `run`, `report`, `phases`; ход сценариев, проверка, возврат стенда |
| `executors.py` | Командные строки исполнителей и вызовы процессов |
| `bare_agent.py` | Агент Конфигуратора без раннера: запуск, SSH, команды, снятие |
| `flag.py` | Флаг замера `E:\stands\.measuring` |
| `describe.py` | Чтение и проверка описаний стендов и сценариев |
| `report.py` | Таблица медиан, трасса раннера со смещениями |
| `stands/<имя>.toml` | Стенды |
| `scenarios.toml` | Сценарии |
| `test_bench.py` | Проверки без платформы: `python scripts/bench/test_bench.py` |

## Флаг замера

Пока идёт `setup` или `run`, скрипт держит файл `E:\stands\.measuring` (`--flag`,
`V8_BENCH_FLAG`) со своим текстом `--flag-text` (`V8_BENCH_FLAG_TEXT`). Текст обязателен и
говорит, кто меряет, например `v8-runner 89ada31d s3 #604`; у каждого параллельного потока
свой текст.

- Флаг уже есть — скрипт ждёт, раз в `--flag-poll` секунд (60) печатает, чей он, и не пишет
  поверх. Ждёт любой чужой текст, в том числе флаги параллельных потоков той же сессии.
- Флаг с тем же текстом, что у нас, скрипт не берёт и выходит: это либо такой же прогон,
  либо остаток упавшего. Удалить его может только человек, проверив, что прогона нет.
- В конце, в том числе при ошибке и Ctrl+C, скрипт удаляет флаг, только если в файле всё ещё
  его текст.

## Стенды

Стенд описан файлом `stands/<имя>.toml`. Рабочий каталог стенда —
`<stands_root>\bench-<имя>` (`--stands-root`, `V8_BENCH_STANDS_ROOT`, по умолчанию
`E:\stands\v8-runner`): там `OWNER.md`, staging, `results\`, `traces\`.

- `[create]` — стенд, который создаёт сам скрипт: `cf` или `dt` шаблона, `disable_support`.
  `setup` кладёт в `bench-<имя>` базу `ib` и проект `project` (git, `v8project.yaml`,
  `v8project.local.yaml`, полная выгрузка `pull --force`, первый коммит) и пишет `OWNER.md` с
  отметкой `created-by: scripts/bench`. Каталог без этой отметки скрипт не трогает;
  `setup --recreate` удаляет и строит заново только свой стенд — вместе с его `results\` и
  `traces\`: сохраните нужные результаты до этого.
- `[existing]` — готовый стенд (`project`, `infobase`). Скрипт его не создаёт и не удаляет;
  правит только модули из наборов и в конце возвращает их в базу и в проект. В истории git
  проекта остаются коммиты `bench …`, память раннера под `workPath` обновляется его же командами.
- `platform` — версия платформы; утилиты ищутся в `<platform_root>\<версия>\bin`
  (`--platform-root`, `V8_BENCH_PLATFORM_ROOT`, по умолчанию `C:\Program Files\1cv8`).
- `[modules]` — именованные наборы `.bsl` (пути от корня набора исходников); на них ссылаются
  сценарии.

Есть стенды `ssl321` (БСП 3.2.1.569 на 8.5.1 из шаблона, поддержка снята), `ka` (КА 8.3.27,
существующий стенд `E:\stands\v8-runner\bench`, проект `p-new`) и стенды замеров выпуска 0.17
(#585) из шаблонов cf, поддержка снята: `kz83`/`kz85` (Бухгалтерия для Казахстана 3.0.75.1),
`unf83`/`unf85` (УНФ 3.0.14.187) на 8.3.27.2342/8.5.1.1529 и `ka85` (КА 2.6.2.72 на 8.5.1.1529).

```powershell
python scripts/bench/bench.py list
python scripts/bench/bench.py setup --stand ssl321 --flag-text "v8-runner 89ada31d s3 #604"
```

`setup --runner-016 <exe>` (`V8_BENCH_RUNNER_016`) готовит ещё проект исполнителя `runner-016`:
`<work>\project-016` с той же базой, `git` и полной выгрузкой этим бинарником. У существующего
стенда `setup` делает только это. Отдельный проект нужен, чтобы два раннера не делили память и
файл версий в одном дереве.

Новая конфигурация — новый файл `stands/<имя>.toml` с `[create]` и наборами модулей,
которые есть в этой конфигурации (`setup` проверит пути).

## Сценарии и исполнители

```powershell
python scripts/bench/bench.py run --stand ka --flag-text "..." `
    [--scenario push-common2 ...] [--executor runner ...] [--reps 3] [--runner <v8-runner.exe>] `
    [--runner-016 <v8-runner.exe>] [--dry-run]
```

По умолчанию — все сценарии, все их исполнители, 3 повтора, раннер из
`$CARGO_TARGET_DIR\release` (или `target\release`). `--dry-run` печатает план и ничего не трогает.
Проект стенда должен быть без незакоммиченных правок; скрипт коммитит каждую свою правку.

| Вид | Что делает исполнитель (время) | Проверка |
| --- | --- | --- |
| `push` | В модули набора добавляется строка-метка; загрузить их в базу и обновить конфигурацию БД | Раннер: пакетный Конфигуратор выгружает изменённое в пустой каталог против `ConfigDumpInfo.xml` до `push`, метка в файлах. Остальные: `v8-runner pull` возвращает метку в исходники |
| `pull` | Метка попадает в базу отдельным пакетным Конфигуратором (вне замера); выгрузить изменённое | Метка в выгруженном файле |
| `status` | Ничего не менялось; ответить, что изменилось | Раннер: `changed_files` у всех наборов 0. Остальные: пустой список изменений |
| `pull-none` | Ничего не менялось; выгрузить изменённое | Раннер: дерево проекта не изменилось. Остальные: в пустом каталоге ничего, кроме файла версий |
| `push-after-pull` | Метка попадает в базу пакетным Конфигуратором, раннер берёт её своим `pull` (вне замера, время — `pull_seconds`); затем `push` без правок | Метка в дереве, дерево не изменилось. Только раннеры |
| `pull-full` | Вся конфигурация в файлы: у раннера `pull --force`, у остальных выгрузка в пустой каталог | Раннер: дерево не изменилось. Остальные: есть `Configuration.xml` |

Файл версий для сравнения (`<cdi>` ниже и проверка `push` у раннера) скрипт каждый раз снимает
с базы заново: `/DumpConfigToFiles <dir> -configDumpInfoOnly`, вне замера, и на
`ConfigDumpInfo.xml` проекта не полагается. Поэтому у исполнителей платформы в `status` пустой
список ожидаем заранее: проверка подтверждает, что команда ответила и список прочитан, а время —
цену вопроса «что изменилось в базе».

| Исполнитель | Как |
| --- | --- |
| `runner` | `v8-runner push`, `pull`, `status`; агент снят (`agent stop --all`) перед каждой командой — разовая команда |
| `runner-live` | То же с живым агентом раннера; первый прогон — прогрев (`rep 0`), в медианы не идёт. Только `push`, `pull`, `pull-none`, `push-after-pull`: `status` агента не спрашивает, полный `pull` файловой базы идёт через `ibcmd` |
| `runner-016` | Другой бинарник раннера (`--runner-016`, выпуск 0.16) в своём проекте `project-016`; перед каждой командой его проект берёт из базы чужие правки (`pull`, вне замера), после — раннер стенда берёт его правки. Без `--runner-016` исполнитель пропускается |
| `agent` | Голый агент: запуск `1cv8 DESIGNER /AgentMode`, SSH, `common connect-ib`, команды, снятие. Время — вся операция, шаги — в `steps` |
| `batch` | Один запуск пакетного Конфигуратора: `/LoadConfigFromFiles <dir> -partial -listFile <list> /UpdateDBCfg -Dynamic-`; `/DumpConfigToFiles <пустой> -update -configDumpInfoForChanges <cdi>`; `... -getChanges <file> -configDumpInfoForChanges <cdi>`; `/DumpConfigToFiles <пустой>` у `pull-full` |
| `ibcmd` | `infobase config import files --partial` и `infobase config apply --force --dynamic=disable`; `infobase config export status --base=<cdi>`; `infobase config export <dir>` у `pull-full`. Для `pull` выгрузки только изменённого в пустой каталог у `ibcmd` нет, исполнитель в этом виде не участвует |

Исполнители платформы грузят только `.bsl`, без описаний объектов, как раннер после #599.
Динамическое обновление конфигурации БД не использует ни один исполнитель: `-Dynamic-`,
`--dynamic-disable`, `--dynamic=disable`, раннер запрещает его сам (`test_bench.py` сторожит
командные строки).

Живой агент раннера переживает команду, только если процесс скрипта не в Job-объекте,
который снимает дочерние процессы: запускайте из обычного терминала, не из песочницы агента.
Если агент не сохранился, у строки `runner-live` будет `warning`.

После каждого сценария скрипт возвращает стенд: исходные тексты модулей в проект,
`v8-runner push` в базу, коммит. Если исполнитель упал, оставшиеся повторы этого исполнителя
пропускаются, стенд возвращается, сценарий идёт дальше.

Новый сценарий — таблица в `scenarios.toml`: `kind` (`push`, `pull`, `status`, `pull-none`,
`push-after-pull`, `pull-full`), `modules`
(набор стенда), `executors`, при необходимости `runner_args` (например `["--deep"]` у
`status`). Новый вид работы — код: метод `<вид>_runner` и `<вид>_other` в `bench.py`, командные
строки в `executors.py`, вид в `describe.KINDS` и `describe.CAN`.

## Результаты

`<work>\results\<стенд>-<время>.jsonl` (`--out`), одна строка на событие:

- `event: start` — путь, версия и SHA-256 раннера, коммиты проекта и репозитория, план;
- `event: measure` — `scenario`, `executor`, `rep`, `warmup`, `seconds` (снаружи процесса),
  `steps` (шаги исполнителя), `ok`, `error`, `verified`, `verify_seconds`; у раннера `rc`,
  `error`, `mode`, `live` (квитанции живого агента), `trace`;
- `event: restore` — возврат стенда; `event: end` — коммит проекта и чистота дерева.

Трассы раннера (`--log-level debug`, `V8TR_ACTION_LOG_FILE`) — в `<work>\traces\`;
`--no-trace` их выключает.

```powershell
python scripts/bench/bench.py report <work>\results\*.jsonl [--steps]
python scripts/bench/bench.py phases <work>\traces\push-push-common2-runner-...log
```

`report` — таблица: строка на стенд и сценарий, столбец на исполнителя, «медиана (число
прогонов)» в секундах. Прогревы, упавшие прогоны и прогоны, у которых проверка не прошла, в
медианы не идут и перечислены под таблицей; с `--no-verify` проверки нет, и прогоны идут в
медианы без неё. `phases` печатает трассу со смещением от начала и паузой после
предыдущей строки.

Исходники и база

Одна и та же конфигурация живёт в двух видах: в базе, где с ней работают, и в файлах, которые лежат под контролем версий. Эта страница о том, какие бывают исходники, что им соответствует в базе, в каких состояниях они бывают и какие команды переводят из одного состояния в другое.

Какие бывают исходники

Единица работы раннера — набор исходников: один каталог с одним предметом. Предметов три, форматов два, и любой предмет бывает в любом формате.

предметXML платформыпроект EDTпакет
конфигурациякаталог с Configuration.xml (14)проект конфигурации (93).cf
расширениетот же формат, объявлено расширением (31)проект расширения, связан с проектом конфигурации (94).cfe
внешние обработки и отчётыкаталог с несколькими обработкамипроект внешних отчётов и обработок (94).epf, .erf

Пакет — четвёртый вид того же предмета: один файл, который платформа умеет применить к базе или разобрать обратно в файлы (29). Снимок всей базы в .dt к исходникам не относится: в нём данные.

Наборы объявлены в v8project.yaml. Тип набора раннер определяет по содержимому маркерных файлов: каталог можно назвать как угодно, тип задаёт Configuration.xml внутри.

format: DESIGNER            # или EDT — формат один на проект
source-set:
  - name: main
    type: configuration
    path: src/cf
  - name: my-ext
    type: extension
    path: src/ext
    installedName: РасширениеВБазе   # имя на той стороне, по умолчанию равно name
    namePrefix: Расш_
    purpose: add-on
  - name: tools
    type: external
    path: src/epf

У формата EDT две ступени. Проект правят в EDT, а с базой платформа обменивается только XML-выгрузкой (92). Экспорт проекта в XML раннер держит у себя как кеш: он не лежит под контролем версий и пересчитывается по изменившемуся.

Что чему соответствует

Расширение ходит по тем же стрелкам с указанием ссылки. Отдельных команд обмена для расширений нет: те же push и pull с именем. Свойства установленного экземпляра правит extensions.

Состояния и переходы

Исходники и основная конфигурация меняются независимо: файлы правят в редакторе, конфигурацию — в Конфигураторе. Отсюда четыре состояния снаружи базы и два способа вернуться к согласию.

stateDiagram-v2
  direction LR
  state "совпадают" as S
  state "исходники впереди" as L
  state "база впереди" as B
  state "разошлись" as D
  S --> L: правка в файлах
  L --> S: push
  S --> B: правка в Конфигураторе
  B --> S: pull
  L --> D: правка в Конфигураторе
  B --> D: правка в файлах
  D --> L: pull
  D --> D: push отклоняется

Петля у «разошлись» — отказ по несовпадению предка. Раннер не выбирает, чья правка важнее: он возвращает к pull, а сводит расхождение система контроля версий.

До первого обмена состояния нет: раннер ещё не знает, как относятся друг к другу каталог и база. status так и говорит. Из этого положения pull идёт всегда, push — только в пустую базу; в непустую без памяти он отказывает и предлагает pull или push --force.

Внутри базы у каждой пары свои состояния. Сохранить изменение в основную конфигурацию и применить его к базе данных — два разных события (3, 5).

stateDiagram-v2
  direction LR
  state "совпадают" as S2
  state "есть непринятое" as P
  state "обновлено динамически" as Y
  S2 --> P: push --no-apply

«Есть непринятое» — штатное состояние: ради него разведены push --no-apply и apply, чтобы реструктуризацию можно было отложить до окна обслуживания. «Обновлено динамически» означает, что новые сеансы получат новую конфигурацию, а работающие останутся на прежней до перезапуска.

Кроме содержимого у ссылки есть собственное состояние: существует ли она с обеих сторон.

Три памяти о прошлом разе

Целиком выгружать и загружать всегда верно и всегда долго. По изменившемуся — быстро, и для этого нужно знать, что изменилось. Знание складывается из трёх памятей: две ведёт раннер, одну платформа.

памятьотвечает на вопроскто ведётгде лежит
хеши исходниковкакие файлы я тронулраннер считает самworkPath, по файлу на набор
поколение базыменялась ли базаплатформа отвечает, раннер записывает (12)workPath, с именем инструмента и операции
файл версий ConfigDumpInfo.xmlчто платформе выгружать зановоплатформа (15)workPath; в каталог исходников подкладывается на время команды

Хеши сравнивают каталог с прошлым разом и дают список файлов для частичной загрузки. Поколение сравнивается только на равенство: совпало — база с прошлого раза не менялась, и выгрузка отвечает «нечего делать» за секунду. Файл версий читает только платформа: по нему она решает, какие объекты перекладывать.

Все три описывают отношение между одним каталогом и одной базой. Поэтому под workPath они лежат по базе: у каждой объявленной базы своя память, и отправка в тестовую не сбивает память о рабочей. Место для этого в конфигурации уже есть: местный слой v8project.local.yaml задаёт workPath, базу по умолчанию и именованные базы, а наборы исходников и формат в нём запрещены.

build/                       # workPath
  infobases/
    default/                 # база по умолчанию
      generation.json        # поколение, чем получено, после какой операции
      hashes/                # хеши исходников по наборам
      ConfigDumpInfo.xml     # файл версий этой пары
    test/
      …

Что делает раннер

Раннер берёт на себя ровно то, чего платформе знать неоткуда: какая база с каким каталогом связана и что в каталоге ваше.

Свой файл версий на пару

Файл версий ConfigDumpInfo.xml хранится у раннера и подкладывается в каталог на время команды. Файл в каталоге становится расходным: он принадлежит последней команде, и в системе контроля версий ему места нет. Перед работой по изменившемуся раннер сверяет отпечаток файла в каталоге со своим.

файл версийкаталогчто делает раннер
нашнашработает по изменившемуся
чужойнашподкладывает свою копию и работает по изменившемуся
нашразошёлсяточка отсчёта устарела — выгрузка полная
чужойразошёлсявыгрузка полная

Выгрузить один файл версий, не трогая остального, платформа умеет (20), и раннер этого не делает: новый файл опишет базу такой, какая она сейчас, и заявит, что все её объекты уже лежат в каталоге. Следующая работа по изменившемуся пропустит настоящие изменения.

Проверка до выбора режима

Наличие файла версий и версия формата в нём читаются до запуска платформы. Файла нет — выгрузка полная, она же его создаст. Версия чужая — тоже полная. Для загрузки та же проверка работает в обратную сторону: формат новее платформы — отказ до запуска с обеими версиями (21).

Ответ описывает случившееся

Платформа может перейти на полную выгрузку сама, и узнать об этом заранее нельзя (17). Поэтому раннер не обещает быстро: ответ называет запрошенный режим и рядом — что вышло на самом деле, с причиной.

Токен хранится с именем инструмента

Рядом с поколением лежит то, чем оно получено. Сравниваются только значения от одного инструмента, чужое считается отсутствием ответа. Сорок нулей пустой базы тоже хранятся как отсутствие ответа, поэтому после работы с пустой базой выгрузка не пропускается.

Слить или заменить

Выгрузка из базы, где правили мимо исходников, должна встретиться с тем, что вы успели наработать. Выбор явный:

слить · pullзаменить · pull --force
что происходитвыгрузка ложится поверх; чего в базе нет, остаётся на местекаталог приводится ровно к базе, лишнее исчезает
когда нужнобазу правили мимо исходников, расхождение надо увидеть в системе контроля версийкаталог считается производным от базы и должен ей соответствовать
формат EDTслияния нет ни в одном режиме: EDT сводит изменения интерактивно (93), поэтому выгрузка либо заменяет проект, либо отказывается

Слияние раннер выполняет чужими руками, и это выбор: выгрузка ложится в рабочий каталог обычным изменением, а сводит его система контроля версий, у которой есть история, трёхстороннее слияние и разметка конфликтов. Раннер отвечает за то, чтобы расхождение стало для неё видимым и безопасным.

Подтверждение разрушения

Разрушение — то, чего нельзя вернуть: правки без фиксации в системе контроля версий, файлы вне её учёта, весь каталог, если он под контролем не находится. Изменение зафиксированного файла сюда не относится: оно видно в разнице и откатывается одной командой.

каталог чистыйтерять нечего, команда идёт
есть незафиксированноекоманда отказывается и называет, что именно потеряется
каталог не под контролем версийпотеряться может всё, отказ на тех же правах

--dry-run показывает это заранее: перечисляет поимённо, что будет перезаписано и что удалено, ничего при этом не трогая.

Поколение до и после

Перед операцией с базой раннер спрашивает поколение и спрашивает его снова после. Если между ними базу правили, ответ называет это, а память о прошлом разе не обновляется: следующая команда снова увидит расхождение.

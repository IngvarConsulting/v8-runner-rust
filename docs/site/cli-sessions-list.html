origin: выбранная база
Активных сеансов нет.

Администрирования кластера целиком у раннера нет: серверы, лицензии, профили безопасности остаются консоли и rac. Сеансы — исключение, потому что без них не бывает применения: окно обслуживания собирается из четырёх команд, sessions deny, sessions terminate --all, apply, sessions allow. Ключ apply --sessions force остаётся для короткого пути: завершить мешающие сеансы в момент, когда платформе нужен монопольный доступ (4).

У кластера три уровня учётных данных, и раннер держит их в местном слое порознь (59): пользователь базы с правами администратора в ключе user секции базы, администратор кластера в cluster.user, администратор центрального сервера в cluster.agent. Каждый запрашивается только той операцией, которой он нужен: sessions list и sessions terminate — кластер; sessions deny и sessions allow — кластер и база, потому что это свойства базы; infobase create в кластере с заполненным списком администраторов — кластер, через SUsr и SPwd строки создания (73) (78). Учётную запись центрального сервера ни одна операция раннера сама не требует; она пригодится, только если сервер её потребует. Отказ называет, какого уровня не хватает.

Исполнителя задаёт вид базы, ключа providers.sessions нет. У кластера это rac по адресу сервера администрирования из секции базы, cluster.ras, с учётной записью администратора кластера (58). Если адрес не объявлен, раннер поднимает ras сам, на своей машине, против агента кластера из строки подключения и гасит его вместе с командой; для этого нужны серверные компоненты платформы той же версии, что кластер (55). У автономного сервера — ibcmd session (103). У файловой базы сервера, ведущего сеансы, нет: sessions отказывает и называет причину, а завершить можно только сеансы через веб-сервер и только в момент apply (5).

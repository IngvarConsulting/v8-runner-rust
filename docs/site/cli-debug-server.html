debug-server

debug-server start подбирает сервер отладки 1С для выбранной базы. Используйте его адрес для отладчика и клиента. stop освобождает аренду собственного dbgs.

Вывод

debug-server start

v8-runner debug-server start --owner-pid 9312

Команда возвращает подтверждённый url, имя базы для отладчика infobase_alias, область scope, владельца owner и поле release. Область client позволяет отлаживать клиент. Область client_and_server охватывает также серверный код, в том числе ServerEmulation у файловой базы.

Свой dbgs берётся из установки тонкого клиента и слушает 127.0.0.1. Раннер проверяет процесс, принадлежность слушателя и ответ rdbg. У таких ответов есть owner_pid и release.session. Повторный вызов для той же рабочей копии, базы и владельца может использовать тот же процесс и выдаёт отдельную аренду. Существующий сервер кластера или явно выбранный внешний сервер возвращает release: null.

Для внешней кластерной базы укажите адрес в infobases.<имя>.debug.url локального файла проекта. Раннер подтверждает связь с выбранной регистрацией. Недоступный адрес даёт debug_server_external_unavailable, отсутствие подтверждённой связи с кластером — debug_server_external_target_unverified. В обоих случаях команда завершает подготовку с отказом. Для внешней кластерной базы без заданного адреса раннер готовит свой dbgs с областью client.

infobase_alias передают в infoBaseAlias запросов rdbg. Для файловой базы это DefAlias, для кластера — зарегистрированное имя из Ref.

v8-runner debug-server start --owner-pid 9312 --dry-run

Превью возвращает action: planned без действующего адреса и аренды. Оно обходится без обращения к серверу и записи состояния. --owner-pid задаёт процесс-владелец и требуется и для превью.

debug-server status

v8-runner debug-server status 5f0c2a9d4e3b4c1f8a7d6e5c4b3a2f10

Передайте release.session из start. Команда проверяет аренду в той же рабочей копии и читает состояние без управления процессом или изменения аренды. Для адреса с release: null токена нет.

Раннер проверяет PID, время запуска, владельца loopback-порта и ответ rdbg. На Linux и macOS он проверяет и владельца соединения, по которому пришёл ответ. После ответа раннер ещё раз проверяет процесс и сокет.

  • ready — готовность подтверждена. В ответе есть адрес, PID, порт и infobase_alias. Обрабатывайте отказ самого подключения: состояние может измениться уже после ответа.
  • unknown — действующая аренда в этой рабочей копии не найдена.
  • stale — записанный процесс завершился или его идентичность сменилась.
  • unverified — готовность подтвердить не удалось. Поле reason уточняет причину. Например, listener_unverified означает, что ОС не подтвердила владельца порта.
debug-server status: ready
url: http://127.0.0.1:12961
pid: 14820

debug-server stop

v8-runner debug-server stop 5f0c2a9d4e3b8c1f8a7d6e5c4b3a2f10

Передайте release.session из ответа start. Действие released означает, что аренда освобождена, а процесс ещё нужен другому сеансу. При последней аренде раннер ждёт конца своего процесса и возвращает stopped и stopped_pid.

Повторный stop возвращает nothing_to_stop. Процесс узнаётся по записи сеанса и времени запуска, чтобы сохранить другой процесс с тем же PID. Для заимствованного адреса release: null завершение отладки не требует stop.

Перед удалением workPath освободите свои аренды.

Без замка рабочей копии

start, status и stop не ждут замка workPath и замка стенда и базу не открывают: отладчик может освободить аренду при отсоединении, даже если в это время идёт push.

Клиент под отладкой

Адрес из ответа передают отладчику и клиенту: launch thin --debug <url> запускает клиент с ключами /DEBUG -http -attach /DEBUGGERURL <url>, и отладчик сам подключает его предметы отладки, зарегистрированные на сервере (112). В примере ниже start выдал свой сервер с арендой. Последней команде передают именно токен из release.session.

v8-runner debug-server start --owner-pid 9312
v8-runner launch thin --debug http://127.0.0.1:12961
v8-runner debug-server stop 5f0c2a9d4e3b8c1f8a7d6e5c4b3a2f10

launch --debug

launch --debug <url> передаёт адрес сервера отладки клиенту предприятия: thin, thick, ordinary или mcp. Ответ launch называет его в debug.url. Перед запуском раннер сервер не проверяет: адрес подтвердил debug-server start, а если сервера уже нет, клиент работает без отладки. launch designer --debug и launch web --debug, адрес не вида http://<хост>:<порт> и ключи отладки в --raw-key рядом с --debug — отказ invalid_argument.

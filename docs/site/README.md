# Сайт документации

Статический сайт, который публикуется на GitHub Pages workflow-ом
[`.github/workflows/pages.yml`](../../.github/workflows/pages.yml) при изменениях в этом каталоге.

- `index.html` — краткое описание инструмента и общая карта взаимодействий.
- `glossary.html` — словарь терминов.
- `platform.html` — тезисы документации 1С со ссылками на ИТС; порождается скриптом (см. ниже), руками не правится.
- `problems.html` — что в поведении платформы мешает работать без рук и чем раннер отвечает.
- `architecture.html` — компоненты системы, кто с кем говорит, цели и исполнители, слои и процессы,
  время жизни; `deployments.html` — выбор вида базы, легенда и общая карта.
- `variant-*.html` — двадцать вариантов на пяти страницах в «Проект → Варианты»:
  файловая база, кластер (включая администрирование), автономный сервер, контейнеры,
  веб-публикация. После каждой схемы — соответствующий локальный YAML;
  общий основной файл задаётся один раз на странице. Все адреса и пути объясняются
  относительно машины раннера. Старые `deployments.html#d-*` перенаправляются на владельцев.
- `sources.html` — виды исходников, что им соответствует в базе, состояния и переходы, три памяти
  о прошлом разе; `pairing.html` и `inside.html` остались перенаправлениями.
- `cli-*.html` — отдельные страницы операций; `cli.html` перенаправляет старые адреса.
- `scenarios.html` — подбор команд под выбранные условия; данные в `data.js`.
- `usecases.html` — сценарии с потоком данных; данные в `usecases.js`, покрытие команд считается кодом.
- `site.js` — общая оболочка справки: дерево разделов, оглавление, мобильное меню
  и полнотекстовый поиск в шапке. `/` фокусирует поиск, Enter открывает первый
  результат, Escape закрывает результаты.
  Значок оформления открывает выбор «Как в системе», «Светлая», «Тёмная»;
  выбор сохраняется локально. Escape закрывает сначала окно оформления, затем меню.
  На широком экране граница дерева перетаскивается; стрелки меняют ширину,
  Home/End выбирают пределы, двойной щелчок возвращает 270 px. Ширина сохраняется.
  Стрелка в шапке скрывает и открывает дерево. На экранах до 1000 px
  дерево по умолчанию закрыто и открывается поверх статьи. На широком экране выбор
  свёрнутого состояния сохраняется отдельно.
  Цвета интерфейса и окно выбора соответствуют справке bsl.js (`dev-theme.ts`, `dev-look.ts`).
  «Раскраска кода» выбирает одну из шести палитр bsl.js с образцом; светлый/тёмный
  вариант следует теме интерфейса. Декоративная раскраска блоков сохраняет текст
  примеров и обновляется вместе с YAML в «Подборе». Выбор палитры сохраняется отдельно.
  При проверке раскраски повторите изменение условий с тем же итоговым YAML:
  генератор заменяет DOM даже при неизменном тексте. Подсветкой владеет `site.js`;
  сравнение только текста не должно пропускать восстановление цветных фрагментов.
  Здесь же счётчик звёзд GitHub с кешем на час.

Названия и адреса страниц берутся из существующего HTML-меню; `site.js` задаёт только
группировку. Без JavaScript остаются исходное меню и все статьи. При добавлении страницы
проверьте её присутствие в меню и на всех страницах оболочки; не заводите второй каталог
названий и адресов. После правки CSS/JS обновляйте версии подключений в HTML и `platform.py`.

Внизу дерева — ссылка Ingvar Consulting. Готовые SVG в `assets/` скопированы из
брендбука https://ingvar.pro/brand: `wordmark-primary.svg` для тёмной темы,
`wordmark-utility-dark.svg` для светлой. Логотипы не перекрашиваются и сохраняют пропорции.

Сайт описывает **только целевое состояние**: как команды, настройки и ответы должны
работать по согласованным решениям. Обязательные правила — в [AGENTS.md](AGENTS.md).
Исходники программы и runtime-схемы не отменяют эти решения. Разрывы реализации
оцениваются отдельно после вычитки, в публичные статьи, примеры и поиск не попадают.
`data.js` содержит только целевую модель; альтернативной ветки текущей реализации нет.

Страница `platform.html` собирается генератором: тезисы, следствия и адреса разделов ИТС лежат
в `platform.py` рядом с сайтом; после правки перегенерируйте страницу:

```bash
python3 docs/site/platform.py > docs/site/platform.html
```

Схемы на страницах «Компоненты», «Исходники и база», «Расстановки» и страницах вариантов нарисованы встроенным
SVG из описаний в `diagrams.py`: узлы задаются координатами, рёбра — якорями на сторонах
узлов или явным путём. Подпись ребра стоит на своей линии: в точке `t` кривой или на заданной
абсциссе `lx`; веер от раннера ставит подписи посередине зазора между раннером и утилитой.
После правки перерисуйте схемы во всех страницах и прогоните проверку наложений — подпись не
должна ложиться на границу рамки, узел или другую подпись:

```bash
python3 docs/site/diagrams.py && python3 docs/site/check_diagrams.py
```

Потоки данных на странице «Сценарии» рисует скрипт самой страницы из `usecases.js`.

Локальный просмотр:

```bash
python3 -m http.server 8765 -d docs/site
```

После изменения статей или данных пересоберите индекс командой
`python3 docs/site/build_search_index.py`. Генератор берёт страницы из HTML-меню
и публичное содержимое из существующих скриптов, включая все варианты целевого
«Подбора». Workflow пересобирает индекс перед публикацией. Проверяйте ссылки
результатов и поиск текста, отсутствующего в заголовках; фильтра в дереве нет.

`install.sh` и `install.ps1` — пользовательская установка CLI из последнего выпуска.
Манифест фиксирует тег; перед заменой проверяются архив, бинарник и запуск.
POSIX-reader принимает canonical schema v2 генератора release_assets.py и отказывает
при неизвестном формате. Тесты: `python3 scripts/test/test_site_install.py`.
Для проверки без изменения обычного каталога задайте `V8_RUNNER_INSTALL_DIR`.

В пользовательском тексте сайта запланированное поведение обозначается только
бейджем «План» (`plan-badge`) у соответствующего раздела. Не дублируйте статус
абзацами о планах, будущем или целевой модели; описания и примеры пишите прямо.

`project.html` — единый владелец справки по файлам проекта: основной и локальный
слои, поиск файла, слияние, наборы исходников, адреса баз и выбор исполнителей.
Раздел «Проект» расположен перед CLI. Страницы команд ссылаются на него.
Порядок обучения: файлы и поиск → минимальный пример → наборы → базы → инструменты
→ исполнители → настройки операций → локальные переопределения. Правила слияния
объясняются после назначения ключей; сокращённые YAML подписываются как фрагменты.
Поиск, слияние и значения ключей описываются по согласованному целевому контракту.
Код и схемы помогают проверить совместимую форму примеров, но не определяют их смысл.
Локальный `push.partialLoadThreshold` заменяет общий при обычном слиянии карт.
Пример `local-push` закрепляет это правило. Реализацию и runtime-схемы здесь не меняем.

На всех `cli-*.html` переключатель CLI / JSON меняет команды и примеры ответов.
Команда JSON использует глобальный `--json-message`; внешний конверт соответствует
`src/command_envelope.rs`. Пользователь согласовал проектирование контракта в справке.
Данные примеров владеют формой `data.infobases[]`: `alias`, `address`, `memory`
(`missing` или `available`), `source_sets[]`. Каждый набор содержит `alias` (null
только при отсутствии набора в проекте), `name`, `states[]` и необязательный
`changed_files` — число изменённых файлов; отсутствие поля не означает ноль.
Состояния: `no_memory`, `unchanged`, `changed`, `pending_changes`, `ahead`,
`untracked`, `dynamic_update`. `no_memory`, `unchanged` и `untracked` используются
отдельно; `changed` допускает `pending_changes`. `memory: missing` отличает
неизвестное сохранённое состояние базы от известного пустого состава наборов.
Форма одинакова для обычного status, deep и all. При расширении сочетаний состояний
сначала согласуйте их смысл; примеры JSON должны сохранять все факты текстового ответа.

Пользователь согласовал удаление `tools.platform.strict` из описываемого контракта.
`path` и `version` — альтернативные способы выбора платформы; оба в итоговом
объединённом документе означают ошибку. Без обоих действует автоматический поиск.
Обычное слияние карт сохраняется: локальный path не снимает общий version.
Оценка разрывов и изменения реализации выполняются отдельной работой.

При переносе вариантов единственный владелец SVG — `diagrams.py:PAGES`,
каталог страниц — исходное HTML-меню. Проверка от повторного появления дубликатов:
20 вариантов имеют по одной схеме. Каждая схема принадлежит
разделу с тем же ID. Генератор заменяет блок по `diagram:` ID, независимо от порядка
разделов и `PAGES`; пропущенные, повторные и смешанные с legacy-блоками ID запрещены.
Регрессии этой привязки проверяются `python3 -m unittest discover -s docs/site -p 'test_diagram_injection.py'`;
в `deployments.html` остаются общая карта и маршруты прежних якорей.
Прямой доступ после остановки кластера из консоли описан в локальном варианте:
от способа запуска сервера схема и YAML не меняются. Не создавайте для него
отдельный раздел или SVG; `d-console-dbms` — только прежний якорь у `d-cluster-local-dbms`.
Веб-публикация не меняет прямой доступ ibcmd к СУБД: им владеет
`variant-cluster.html#direct-dbms`. Не добавляйте отдельные SVG/YAML для этого
сочетания; при вычитке проверяйте ссылку на общий вариант. Старый
`d-cluster-web-dbms` сохранён только на абзаце со ссылкой.
Готовой веб-публикацией без управления владеет `variant-publication.html#d-web-remote`:
только `web.url` для launch, без webinst и управляющих рёбер. Условиями управления через монтирование владеет `variant-publication.html#d-web-mounted`;
контейнерным веб-сервером — `variant-publication.html#d-web-docker`. При вычитке
проверяйте, что URL не описан как запрет прав: publish недоступен из-за отсутствия
параметров управления в этом примере. Геометрию `d-web-remote` проверяет `check_routes`.
Сценарием двух публикаций одной ИБ владеет `variant-publication.html#d-web-dual`.
Именованные `web.publications` и `--publication` описывают согласованное поведение;
бейдж «План» остаётся метаданными раздела. YAML и CLI пишутся прямо как примеры этого
контракта; текущая доступность ключей не добавляет оговорок или обходных путей.
Проверка от подмены одной ИБ двумя: в схеме два HTTP пути и два каталога
с default.vrd сходятся к одному cluster/Ref; в примере одно объявление origin.
Геометрию проверяет `check_routes`; project и CLI ссылаются на этого владельца.
Двумя разными базами с отдельными публикациями владеет
`variant-publication.html#d-web-two-infobases`: рабочий пример выбирается
через `--infobase`; `--publication` выбирает публикацию внутри одной ИБ.
Общая геометрия пары принадлежит `d_web_pair`. Guard против смешения сценариев:
`test_two_publications_keep_the_infobase_identity` проверяет один общий Ref
у двух публикаций одной ИБ и два разных Ref у двух ИБ; `check_routes` проверяет
геометрию обеих схем. URL-only пример не обещает управление каталогами Apache.
Легенда «Как читать схемы» имеет одного владельца — `glossary.html#d-legend`;
входящие ссылки ведут туда, а прежний `deployments.html#d-legend` сохраняет
переход и ссылку для чтения без JavaScript. При регенерации проверяйте, что
`diagram:legend` остаётся только в словаре.
Примеры main/local разбираются YAML и проверяются соответствующими JSON Schema.
Общей картой владеет `diagrams.py:general_map`: SVG должен совпадать на страницах
index, architecture и deployments. Конфигуратор и AgentMode — отдельные процессы
с разными каналами запуска. Форматы исходников XML и EDT — два артефакта;
1cedtcli связан с обоими для импорта/экспорта. Файловая база и база в СУБД общие
для разных режимов доступа, без дополнительных хранилищ «для ibsrv».
Кластер и ibsrv используют одну базу поочерёдно; условие остановки кластера
сохраняется у прямого доступа ibcmd к кластерной ИБ. Apache/IIS подключается
к файловой базе или кластеру, а ребро webinst обозначает публикацию.
При проверке карты контролируйте эти связи
и отсутствие пересечения рёбер с промежуточными узлами: проверка геометрии подписей
сама по себе этого не гарантирует.
Утилиты, подключения и хранилища размещаются отдельными полосами. Подпись должна
пересекать только своё ребро: `check_diagrams.py` проверяет её принадлежность
и запрещает чужую линию под подписью. Подписи запуска стоят на горизонтальных
подходах к утилитам, а не в общем веере рядом с раннером.
Положение ручного маршрута задают `general_map`, `d_docker_cluster`, `d_file_web` и `d_cluster_web`; `Diagram.rounded_path` только
скругляет его заданные повороты, не выбирает расположение узлов или маршрут.
У общей карты и схем `d-docker-cluster`, `d-file-web`, `d-cluster-web` линия выходит и входит по нормали к грани с прямыми участками
не короче 30 единиц SVG. Касательные на стыках L/C/Q совпадают по направлению
(допуск округления — 1°); вырожденные касательные запрещены.
У прямых кривых контрольные точки идут по порядку без обратного хода;
длина управляющих отрезков ограничена свободным зазором между блоками.
Ручной маршрут обязан начинаться в объявленном `fa`
и заканчиваться в `fb`;
порты капсул лежат на нарисованном контуре: боковые — на средней линии,
верхние и нижние — на прямом участке между скруглениями. Проверка портов
в `check_diagrams.py` запрещает начало или конец в углу bounding box.
Точки входа на одной грани разделены минимум на 18 единиц и отступают от углов
и волнистого края. `check_diagrams.py` проверяет эти условия и пересечения
маршрутов с узлами, включая собственные исходный и целевой блоки.
Причина оторванных стрелок и подписей — независимые ручные координаты.
Маршруты контейнерного кластера начинаются и заканчиваются в `Diagram.anchor`,
подписи стоят на отдельных горизонтальных участках. Общая проверка `check_routes`
для карты, `d-docker-cluster`, `d-file-web` и `d-cluster-web` не допускает возврата этого дефекта; негативные
тесты в `test_diagram_injection.py` проверяют отрыв начала и подписи,
а также перекрытие наконечника подписью. Подписи отступают от обоих концов
стрелки минимум на 10 единиц SVG; этот зазор проверяет `check_routes`.
В `d-file-web` и `d-cluster-web` локальный тонкий клиент имеет два отдельных пути:
напрямую к базе (File или TCP к кластеру) и HTTP к веб-серверу. Проверка
`test_local_client_has_direct_and_web_paths` защищает от пропуска одного из них.
В `d-cluster-web` сетевые каналы имеют разные точки входа в блок менеджера; подписи стоят
на своих подходах. Файловые и сетевые маршруты могут пересекаться, но чужие
линии не должны проходить под подписью. Пунктир и непрерывная линия различают
сетевые и файловые связи, не заменяя подписи и направления стрелок.
Прямые участки автоматических рёбер задаются через `exit_stub` и `entry_stub`;
нулевые значения сохраняют прежнюю геометрию остальных схем. Разбор M/L/C/Q
принадлежит `Diagram.path_segments`: его используют отрисовка и проверка стыков.
При добавлении варианта проверяйте общую машину, пути и доступность портов у схемы
и примера вместе. Разделы RAS сохраняют согласованные бейджи «План».

Кластерные варианты разделены по наличию прямого доступа к СУБД: прежний якорь
ведёт на подключение через работающий кластер, `-dbms` — на ibcmd при остановленном кластере. Штатной геометрией
владеют генераторы кластерных развёрток; режимом остановки — `d_cluster_stopped`.
Параметр `dbms` выбирает только прямой канал ibcmd без активных клиентов и кластерных рёбер. Без него сама СУБД и канал rphost
сохраняются. Адрес DBMS в YAML разрешается с машины раннера (для Docker —
опубликованный порт хоста); физическое имя БД не подменяется Ref. Наличие канала
не означает автоматический выбор ibcmd или поддержку им всех операций.
Проверка от повторного смешения каналов: для каждого раздела разобрать следующий
local YAML и проверить соответствие `dbms` прямому ребру ibcmd → DBMS; для File
проверяется ibcmd → файловый каталог, для standalone — только объявленные шлюзы
и выбранный exchange. Это дополнение к проверке геометрии и схем YAML.

Страницы CLI начинаются с назначения команды и общего переключателя CLI / JSON.
Пилот единого шаблона применён к `init`, `push` и `infobase create`:

1. Все варианты вызова идут подряд, каждый — под заголовком со знаком `>`.

2. Особенности исходников показываются только при различии действий между
   Конфигуратором и EDT. Определения форматов принадлежат словарю.
3. «Исполнение» описывает проверки, последовательность действий, исполнителя,

   Каждая карточка называет условия, применимые вызовы, фактически изменённое
   состояние и парный пример CLI / JSON. У ошибки также указаны причина и код,
   код выхода CLI и обоснованный следующий шаг. Общий случай описывается один раз.

Все ответы находятся после всех вызовов. Вызов ссылается на карточку результата,
карточка — на подходящие вызовы. Отдельная таблица, повторяющая эти классы, не нужна.
Диаграмма последовательности дополняет сложное исполнение, если облегчает чтение.
Старые якоря и примеры при перестройке сохраняются. Остальные страницы переходят
на этот шаблон после вычитки пилота.

Целевой `clone` использует `src/cf` по умолчанию,
`--source-dir` меняет этот путь. `clone --from` объявляет проект и выполняет первую
выгрузку. Init не создаёт ИБ, clone проверяет существование конкретных целей,
а не пустоту всего каталога. Синтаксис и результаты следуют согласованным сценариям.
Объяснения аналогии с Git не заменяют справку по параметрам; старая ссылка `model`
ведёт к владельцу модели исходников.

Единственный владелец переключения формата — блок `data-output-format` в `site.js`:
он выбирает полный JSON-конверт из `#output-examples` страницы и восстанавливает
исходный CLI-текст. Он не создаёт успешный ответ и не угадывает поля команды.
Каждый `pre[data-output-example]` ссылается на пример по ID и на форму `data`

`docs/schemas/command-data/`; если целевой результат отличается, его форма принадлежит
примеру страницы (`data-output-schema="planned"`). Это техническая метка проверки,
а не основание писать в статье о разрыве реализации. Длительности, версии,
идентификаторы и пути в примерах иллюстративны. Сокращённый CLI-ответ подписывается
как фрагмент; JSON показывает конверт этого результата.

### Классы ответов CLI

Все 26 страниц CLI описывают предметные классы для вариантов команды. В едином
шаблоне владельцы классов — карточки результатов, на остальных страницах —
перечень и связанные примеры до переноса на шаблон.
Общий словарь формы ответа, причин отказа и границы CLI/JSON находится
в `glossary.html#command-responses`. Перечень описывает результат для пользователя,
а не достижимость кодов в сегодняшнем producer. Отказ, сбой, предупреждение,
пропуск и превью должны сохранять собственный смысл; один успешный пример
не заменяет перечень. Ошибка парсера не получает выдуманный JSON-конверт.

Предметные инварианты: `ok: false` не означает откат; флаги выполненных шагов
сохраняют факт выполнения. `uncertain` означает неподтверждённый результат,
`issues_found` отличается от сбоя проверки. PID не подменяет готовность клиента,
а путь результата — факт его создания. Preview не запускает платформу и не меняет базу.

Reintroduction guard: HTML конкретной команды владеет применимостью классов,
словарь — общими формами. `test_cli_reference.py` проверяет полноту страниц,
парные CLI/JSON-примеры, конверт, совместимые схемы и предметные инварианты.
Для единого шаблона проверка также требует последовательную группу вызовов перед
исполнением и ответами, условия карточек, ссылки на вызовы и правильное разделение
успешных и неуспешных конвертов. Это предотвращает возвращение перемешанных
разделов под другими заголовками. Соответствие условий карточки смыслу вызова
проверяется отдельно при вычитке; наличие ссылки само по себе его не доказывает.
Проверка текущего producer не является проверкой правильности целевого контракта.

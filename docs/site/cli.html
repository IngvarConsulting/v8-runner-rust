Словарь команд

Проект нового набора команд: тех же действий, названных так, как их уже знают и человек, и языковая модель. Страница описывает замысел, а не сегодняшнее поведение.

Зачем менять

У командной строки три потребителя: сценарии непрерывной сборки, человек за терминалом и Unica, которая ходит в раннер за пользователя. У всех троих одна беда — чтобы понять, что делает команда, нужно прочитать справку. build не собирает, а загружает в базу. dump не сохраняет, а забирает из базы. --name в соседних подкомандах значит разное.

Языковая модель знает гит. Это знание досталось даром, и его можно занять: если команда называется так же и ведёт себя так же, объяснять нечего.

Интерфейс MCP не меняется. Опубликованные имена инструментов остаются прежними ради обратной совместимости. Новый словарь — только у командной строки; основной путь языковой модели пойдёт через Unica, а Unica вызывает командную строку.

Принцип: ложный друг хуже незнакомца

Языковая модель действует по усвоенной семантике. Увидев pull, она предполагает слияние и сохранность несохранённой работы. Если команда с этим именем заменяет дерево целиком, знание сработает против неё — и тем вернее, чем лучше она знает гит.

Поэтому имя из гита берётся только там, где по нему можно действовать не читая справку. Где поведение расходится — либо приводим поведение к имени, либо берём другое имя.

Проверка для каждого имени. Если человек, знающий гит и не читавший нашу документацию, выполнит команду — получит ли он то, чего ожидал? Если нет, имя не берём, каким бы удобным оно ни казалось.

Информационная база — это не голый репозиторий

Аналогия сходится точнее, чем кажется. В базе хранятся две конфигурации: основная, которую правят, и конфигурация базы данных, с которой работают пользователи. Это в точности устройство репозитория с рабочим деревом:

у насв гите
каталог исходниковрабочее дерево
основная конфигурацияветка на той стороне
конфигурация базы данныхрабочее дерево на той стороне
каждое расширениеотдельная ссылка на том же удалённом

Отсюда следует то, что знает каждый, кто пушил в неголый репозиторий: отправка обновляет ветку, но не обновляет рабочее дерево на той стороне. Ровно поэтому /UpdateDBCfg — отдельный шаг, а не часть загрузки.

Расширения — ссылки на той стороне

У конфигурации и у каждого расширения своя пара «основная ↔ база данных»: это видно по самой платформе, у /CompareCfg есть типы ExtensionConfiguration и ExtensionDBConfiguration. Значит база держит не одну ссылку, а несколько независимых, и выбор — это указание ссылки.

v8-runner push                    все наборы исходников
v8-runner push main               только конфигурацию
v8-runner push my-ext             только расширение
v8-runner push my-ext:ИмяВБазе    разовая подмена соответствия
v8-runner pull --all              включая все расширения

Имя здесь и имя там — разные имена

Сегодня этого различия в конфигурации нет, и оно расползлось по ключам команд. --name означает имя набора исходников в одной подкоманде и имя, известное платформе, — в соседней; рядом пришлось завести ещё и --installed-name.

Гит решил это тридцать лет назад: соответствие объявляется один раз, а не передаётся при каждом вызове.

source-set:
  - name: my-ext
    type: extension
    path: src/ext
    installedName: РасширениеВБазе   # по умолчанию равно name
    namePrefix: Расш_
    purpose: add-on

Объявив namePrefix и purpose там же, мы получаем и создание расширения отправкой — как git push -u создаёт отсутствующую ветку. Отдельная команда «создать расширение» становится не нужна.

Появляется слово для того, у чего его нет

Расширение, установленное в базе, но отсутствующее в проекте, сегодня никак не называется. В словаре ссылок оно называется естественно:

$ v8-runner status
infobase: File="/srv/ib/demo"

  main      → ЖивоеИмяКонфигурации   3 файла изменено

  —         → Patch_007              есть в базе, нет в проекте

Отказы, которые учат

Самое ценное в гите — не команды, а его отказы: они называют следующий шаг. Тот же приём закрывает трудность, которую мы разбирали отдельно: базу правили в Конфигураторе мимо исходников.

$ v8-runner push
✖ Отправка отклонена: база ушла вперёд с вашей последней выгрузки
  поколение базы:  7f3a…
  ваше:            2b91…
  сперва выполните: v8-runner pull

Для Unica тот же отказ приходит разбираемым, чтобы не пришлось читать прозу:

{"ok": false,
 "error": {"kind": "non_fast_forward",
           "base_generation": "7f3a…", "local_generation": "2b91…",
           "next": {"command": "pull", "source_set": "main"}}}

Командная строка — это и есть интерфейс для Unica. Значит у каждой новой команды полная форма ответа в JSON, а подсказка следующего шага — поле, а не фраза в тексте. Текстовая строка остаётся человеку и сценариям сборки.

Слом: синоним или отказ

Старые имена работают ещё один цикл скрытыми синонимами: в справке их нет, при вызове они печатают, чем их заменили. Но есть случай, где синоним недопустим.

Имя, сменившее смысл, синонима не получает — оно получает отказ. Старый init создавал информационную базу, новый заводит проект. Промолчать здесь значит выполнить не то, о чём просили, поэтому init на старом сценарии остановится и назовёт infobase create.

Что намеренно не стало метафорой

У гита тоже есть gc и bisect — не всё обязано быть аналогией. Не взяты:

заманчивое имяпочему не взято
checkout для loadв гите это местное действие, а загрузка .cf меняет базу. Обманывает в опасную сторону
merge для load --mode merge/MergeCfg с файлом настроек — совпадение только в букве
push --force для --full-rebuildв гите значит «перезапиши ту сторону», у нас — «пересобери заново здесь»
remote отдельной командойдва слова для одной вещи. Адрес базы виден в status, создание — infobase create
stash, commit, logработа с системой версий остаётся за самой системой версий. Раннер её не заменяет

Одно место, где имя дешевле поступка

push --delete опаснее своего гитового тёзки. Удаление ветки в гите дёшево и достаётся из журнала ссылок. Удаление расширения из базы может увести данные, которые оно добавляло, и журнала ссылок там нет. Имя знакомое, цена другая — значит эта команда спрашивает подтверждение жёстче, чем гит, по тем же правилам, по которым выгрузка отказывается уничтожать незафиксированное.

Чего словарь не даёт и что должно быть раньше

pull обещает слияние. На формате Designer платформа это умеет: выгрузка по изменившемуся пишет прямо в каталог и трогает только изменившиеся объекты. На формате EDT слияния нет ни в одном режиме — каждая выгрузка заменяет дерево целиком.

Значит либо слияние для EDT появляется раньше переименования, либо pull на EDT с первого дня работает наполовину и требует --force. Мы выбираем первое: главное имя нового словаря не должно лгать на половине проектов.

Так же status опирается на привязку каталога к базе и на журнал поколений, а diff — на замер цены /CompareCfg на живой базе. Это работы, которые словарь делает осмысленными, но не заменяет.

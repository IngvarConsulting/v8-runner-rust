Словарь команд

Команды раннера названы так, как их уже знают человек и языковая модель: словарём гита. Это не украшение — это способ не объяснять то, что собеседник знает.

Почему словарь гита

У командной строки три потребителя: сценарии непрерывной сборки, человек за терминалом и Unica, которая ходит в раннер за пользователя. Всем троим нужно одно — понимать, что делает команда, не читая справку.

Языковая модель знает гит. Это знание досталось даром, и его можно занять: если команда называется так же и ведёт себя так же, объяснять нечего. Человеку это выгодно ровно настолько же, а сценариям сборки — потому что знакомое имя реже используют неверно.

У интерфейса MCP свой словарь. Имена его инструментов — опубликованный контракт, у которого есть свои потребители, и меняются они по своим правилам. Словарь этой страницы принадлежит командной строке. Основной путь языковой модели идёт через Unica, а Unica вызывает командную строку.

Ложный друг хуже незнакомца

Языковая модель действует по усвоенной семантике. Увидев pull, она предполагает слияние и сохранность незафиксированной работы. Команда с этим именем, заменяющая каталог целиком, обратила бы её знание против неё — и тем вернее, чем лучше она знает гит.

Поэтому имя из гита стоит только там, где по нему можно действовать не читая справку. Где поведение разошлось бы — либо поведение приведено к имени, либо взято другое имя.

Проверка для каждого имени. Если человек, знающий гит и не читавший эту документацию, выполнит команду — получит ли он то, чего ожидал? Если нет, имя не берётся, каким бы удобным оно ни казалось.

Информационная база — это неголый репозиторий

Аналогия держится не на созвучии, а на устройстве. В базе хранятся две конфигурации: основная, которую правят, и конфигурация базы данных, с которой работают пользователи. Это в точности репозиторий с рабочим деревом:

у насв гите
каталог исходниковрабочее дерево
основная конфигурацияветка на той стороне
конфигурация базы данныхрабочее дерево на той стороне
каждое расширениеотдельная ссылка на том же удалённом

Отсюда следует то, что знает каждый, кто отправлял в неголый репозиторий: отправка обновляет ветку, но не обновляет рабочее дерево на той стороне. Поэтому приведение базы данных к основной конфигурации — отдельный шаг, а не часть отправки. Не по нашему решению: так устроена платформа, и словарь это отражает, а не выдумывает.

Команды

Состояние — не меняют ничего

командачто делает
statusсостояние пары: к какой базе привязан каталог, что разошлось, что потеряется при замене. Отвечает по своей памяти; --deep спрашивает платформу
diffподробное расхождение: основная конфигурация против базы данных, против конфигурации поставщика, против файла
versionверсия раннера

status — первая команда, которую выполняют, когда непонятно, что происходит. Она поэтому обязана быть дешёвой: платформу не запускает, базу не трогает.

Обмен с базой

командачто делает
pullбаза → исходники. Сливает пообъектно и отказывается, когда потерялась бы работа, которую система версий не вернёт
pull --forceприводит каталог ровно к базе, уничтожая лишнее
pushисходники → основная конфигурация, затем приведение базы данных. Отказывается, если база ушла вперёд
push --no-applyостанавливается на основной конфигурации: реструктуризацию запускают в окно обслуживания
push --delete <ссылка>убирает расширение из базы
applyприводит базу данных к основной конфигурации и больше ничего
load --path <файл>применяет готовый .cf или .cfe к базе

load не часть push намеренно. У него свои режимы платформы — load, merge, update, — и merge здесь означает объединение конфигураций по файлу настроек, а не трёхстороннее слияние. Два разных смысла слова в одном глаголе — та самая ловушка, которой словарь избегает.

Начало работы

командачто делает
initзаводит проект здесь: конфигурацию и наборы исходников. Наружу не выходит
clone --from <строка>заводит проект из существующей базы: привязка и первая выгрузка
infobase createсоздаёт саму информационную базу и рабочую область EDT

Граница между init и infobase create проведена по тому же признаку, что у гита: init — местное действие, оно заводит рабочую копию и ничего снаружи не создаёт. Создание базы выходит за пределы каталога, поэтому живёт под infobase, где собрано всё, что делается с базой целиком.

infobase restoreзагружает базу из .dt, уничтожая текущие данные

Расширения — ссылки на той стороне

У конфигурации и у каждого расширения своя пара «основная ↔ база данных». Это свойство платформы: у сравнения конфигураций есть отдельные типы для конфигурации расширения и для конфигурации базы данных расширения. Значит база держит не одну ссылку, а несколько независимых, и указание ссылки — обычный довод команды.

v8-runner push                    все наборы исходников
v8-runner push main               только конфигурацию
v8-runner push my-ext             только расширение
v8-runner push my-ext:ИмяВБазе    разовая подмена соответствия
v8-runner pull --all              включая все расширения

Имя здесь и имя там — разные имена

Набор исходников называется так, как удобно проекту. Расширение в базе называется так, как его завели, и переименовать его нельзя, не затронув установленные копии. Это два имени, и они расходятся не по недосмотру, а по существу.

Соответствие поэтому объявлено один раз, рядом с набором исходников, а не передаётся ключом при каждом вызове:

source-set:
  - name: my-ext
    type: extension
    path: src/ext
    installedName: РасширениеВБазе   # по умолчанию равно name
    namePrefix: Расш_
    purpose: add-on

Там же объявлены namePrefix и purpose — сведения, которых в исходниках нет, а платформе они нужны при заведении расширения. Раз они объявлены, отправка создаёт отсутствующее расширение сама, как git push -u создаёт отсутствующую ветку. Отдельная команда «создать расширение» не нужна: создание — это следствие первой отправки, а не самостоятельное намерение.

У расширения в базе без проекта есть имя

Расширение, установленное в базе, но отсутствующее в проекте, — обычное состояние, а не сбой: его мог поставить кто-то другой или оно пришло с обновлением. Словарь ссылок называет его так же, как гит называет ветку, за которой никто не следит:

$ v8-runner status
infobase: File="/srv/ib/demo"

  main      → ЖивоеИмяКонфигурации   3 файла изменено
  my-ext    → РасширениеВБазе        совпадает
  patch-01  → Patch_01               база ушла вперёд — сперва pull
  —         → Patch_007              есть в базе, нет в проекте

Отказ называет следующий шаг

Самое ценное в гите — не команды, а его отказы: они не просто запрещают, а говорят, что делать. Тем же приёмом закрывается трудность, знакомая каждому, кто работает и в Конфигураторе, и в исходниках: базу правили мимо каталога.

$ v8-runner push
✖ Отправка отклонена: база ушла вперёд с вашей последней выгрузки
  поколение базы:  7f3a…
  ваше:            2b91…
  сперва выполните: v8-runner pull

Расхождение поколений — это несовпадение предка, и у него уже есть общеизвестное имя. Человеку не нужно узнавать новую ошибку: он видел её в гите.

Командная строка — это интерфейс

Unica ходит в раннер через командную строку, значит командная строка — не только человеческий вывод, но и программный. Поэтому подсказка следующего шага приходит полем, а не фразой:

{"ok": false,
 "error": {"kind": "non_fast_forward",
           "base_generation": "7f3a…", "local_generation": "2b91…",
           "next": {"command": "pull", "source_set": "main"}}}

Текстовая строка остаётся человеку и сценариям сборки, разбирать её никому не нужно.

Что намеренно не стало метафорой

У гита тоже есть gc и bisect — не всё обязано быть аналогией. Имена ниже выглядят подходящими и не взяты:

имяпочему не взято
checkout для loadв гите это местное действие, а применение .cf меняет базу. Обманывает в опасную сторону
merge для объединения конфигурацийобъединение по файлу настроек — совпадение с трёхсторонним слиянием только в букве
push --force для полной пересборкив гите значит «перезапиши ту сторону», а полная пересборка — это «посчитай заново здесь»
remote отдельной командойвышло бы два слова для одной вещи. Адрес базы виден в status, действия с базой собраны под infobase
stash, commit, logработа с системой версий принадлежит самой системе версий. Раннер её не подменяет и в неё не пишет

Где имя дешевле поступка

push --delete опаснее своего тёзки. Удаление ветки в гите дёшево и достаётся из журнала ссылок. Удаление расширения из базы уводит данные, которые оно добавляло, и журнала ссылок там нет. Имя знакомое, цена другая — поэтому эта команда спрашивает подтверждение жёстче, чем гит, по тем же правилам, по которым выгрузка отказывается уничтожать незафиксированное.

Это единственное место, где словарь сознательно расходится с поведением тёзки. Расхождение здесь в сторону осторожности: знакомое имя ускоряет руку, и цена ошибки должна быть возвращена предупреждением.

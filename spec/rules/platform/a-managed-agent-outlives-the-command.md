# Процесс своего агента и его сессия переживают команду

Если агента Конфигуратора поднял сам раннер, то после работы команда не снимает ни его
процесс, ни его сессию SSH. Их держит сторож (`INV.PLATFORM.A-LIVE-AGENT-DIES-WITH-ITS-KEEPER`).
Следующая команда того же ключа (`INV.PLATFORM.A-LIVE-AGENT-IS-TAKEN-ONLY-BY-ITS-KEY`) передаёт
запросы агенту через сторожа. Подключение агента к базе тоже переживает команду
(`INV.PLATFORM.A-LIVE-AGENT-STAYS-CONNECTED-BETWEEN-COMMANDS`); если агент на `common connect-ib`
отвечает, что подключение уже есть, это считается подключением. Пока агент подключён, он
держит базу как сеанс Конфигуратора с учётными данными, с которыми подключился.

Это экономит запуск процесса и открытие сессии: на КА 8.3.27 6,4 с и 2,8 с из 9 с
([замер](../../../references/1c/confirmed-runtime-measurements.md), раздел о процессе агента
между командами).

С агентом говорит только сторож. Команда обращается к сторожу через локальный канал, открытый
только своей учётной записи ОС: именованный канал на Windows, сокет Unix в других ОС. Сам вход
к агенту по SSH раннер не защищает сверх того, что делает платформа. Агент пускает по
пользователю базы и его паролю, а к базе без пользователей — с пустым логином
([замер](../../../references/1c/confirmed-runtime-measurements.md), раздел об аутентификации
агента; [вход пользователем ИБ](../../../references/1c/designer-agent/README.md)). Нарушитель на
той же машине может так же легко поднять своего агента на этой базе и подключиться к нему, и
раннер ему для этого не нужен. Поэтому защищаться здесь раннеру нет смысла.

Подключённого агента (`tools.designer_agent.attach`) и шлюз автономного сервера раннер не
поднимает и временем их жизни не управляет.

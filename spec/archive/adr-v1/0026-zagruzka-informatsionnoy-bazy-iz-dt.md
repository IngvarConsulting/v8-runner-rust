# ADR-0026: Загрузка информационной базы из DT

- Статус: `accepted`
- Дата: `2026-09-11`
- Связанные решения: [ADR-0005](0005-razdelit-cli-i-mcp-publichnye-poverhnosti.md), [ADR-0006](0006-sohranyat-transportno-neytralnyy-use-case-sloy.md), [ADR-0008](0008-derzhat-platformennye-backend-dsl-otdelno-ot-orchestration.md), [ADR-0011](0011-eksklyuzivnoe-vladenie-workpath-na-vremya-komandy.md), [ADR-0015](0015-atomarnaya-publikatsiya-dump-artifacts-cherez-staging-backup.md), [ADR-0024](0024-tipizirovat-eksport-konfiguratsii-i-snimka-ib.md)

## Контекст

ADR-0024 ввёл `infobase dump`: полная ИБ вместе с данными уходит в переносимый
DT-файл. Обратной операции не было ни в одном режиме — `load` принимает только
`.cf`/`.cfe`, `init` входа DT не принимает. Выгрузка есть, возврата нет.

Замер на 8.3.27.2074 (файловая ИБ, выброшенные копии) показал, что платформа
умеет загрузку в двух утилитах:

| | `ibcmd infobase restore` | Designer `/RestoreIB` |
|---|---|---|
| цель существует | заменяет, `rc=0`, без вопросов | заменяет, `rc=0`, без вопросов |
| цель отсутствует | `rc=255` «Отсутствует файл базы данных», каталог и `1Cv8.cgr.cfl` остаются | создаёт базу, `rc=0` |
| цель отсутствует + `--create-database` | создаёт и загружает, `rc=0` | ключа нет, создаёт всегда |
| вход не читается | `rc=255` «Файл не обнаружен» | не мерено |
| завершение сеансов | `--force`, `--session-terminate-message` | ключа нет |

Два факта из этой таблицы определяют решение:

1. **Замена не имеет шлюза ни у одного провайдера.** Опечатка в пути стирает
   данные без предупреждения.
2. **Создание ведёт себя по-разному.** Designer создаёт всегда, IBCMD без
   `--create-database` отказывает. Один и тот же вызов даёт разный исход в
   зависимости от выбранного провайдера.

## Решение

Ввести transport-neutral use case:

```text
RestoreInfobaseSnapshot {
  input,
  target_mode: Create | Replace
} -> ИБ
```

Точная CLI grammar:

```text
v8-runner infobase restore --input <path.dt> (--create | --replace) [--dry-run]
```

Canonical command identity — `infobase.restore`. Публикуется только в CLI; MCP
surface не расширяется.

**Ровно один режим цели обязателен, и он проверяется против наблюдаемой цели.**
Режим — шлюз на стороне runner, потому что ни один провайдер не спрашивает.
`--create` при существующей ИБ и `--replace` при отсутствующей отклоняются как
`invalid_argument`; молчаливого перехода к другому случаю нет. Так же снимается
расхождение провайдеров: исход вызова задаётся режимом, а не тем, кто выбран.

Наличие файловой цели определяется файлом `<infobase>/1Cv8.1CD`. Серверную ИБ без
процесса наблюдать нельзя, поэтому там режим принимается на слово вызывающего, а
последнее слово остаётся за платформой.

Проверка цели идёт **до** выбора провайдера и повторяется под workspace lock.
Причина: staging-шага здесь нет. Экспорт по ADR-0015 пишет в приватный staging и
публикует атомарно, а загрузка идёт прямо в ИБ, и отменить её нечем. Режим —
единственная защита вызывающего, поэтому он проверяется дважды, а не один раз.

Implemented provider — Designer `/RestoreIB`, evidence `live_verified`. IBCMD
`infobase restore` запускается вживую, но остаётся `experimental` с тем же
обоснованием, что IBCMD DT export в ADR-0024: нет проверки отсутствия активных
сеансов. Адаптер IBCMD намеренно **не добавлен**: недиспетчеризуемый адаптер был
бы мёртвым слоем, он придёт вместе с preflight-ом.

`target_state` различает `created` и `replaced`. Упавший провайдер даёт
`uncertain`: сколько данных он успел заменить, не наблюдаемо.

## Последствия

- У выгрузки появляется возврат, и пара `dump`/`restore` закрывается.
- Принудительное завершение сеансов не публикуется: ключ IBCMD `--force` не
  проброшен, у Designer такого ключа нет. Занятая ИБ отвечает ошибкой платформы.
  Это осознанный разрез, а не упущение: пробросить `--force` — значит решить,
  как выглядит расхождение возможностей провайдеров, а живьём завершение сеансов
  здесь не проверялось.
- Общий текстовый рендер `infobase` получил имена полей для пути и факта
  применения (`output`/`published` против `input`/`restored`), чтобы у операций
  не появилось двух владельцев вывода. Текст экспорта не изменился.
- `ExportIntent`, `ExportProvider`, `ExportTargetState` и словарь
  implementation/readiness/evidence переиспользованы, а не продублированы.
  Их имена говорят «export», хотя модуль описывает перенос ИБ в обе стороны;
  переименование — отдельная задача, не часть этой.

## План реализации

1. Designer DSL: `/RestoreIB`.
2. Домен: `RestoreTargetMode`, request/result/plan, переиспользование словаря.
3. Use case: валидация входа и цели, выбор провайдера, загрузка, превью.
4. CLI: команда, identity, провод, рендер, envelope.
5. Тесты: parse, оба режима, все отказы, превью без dispatch.
6. Документы: `docs/CAPABILITIES.md`, `README.md`, `SKILL/`, инварианты.

## Верификация

- [x] Замена существующей файловой ИБ проходит через Designer и даёт
      `target_state=replaced`, `restored=true`.
- [x] Создание отсутствующей ИБ даёт `target_state=created`.
- [x] `--create` при существующей ИБ и `--replace` при отсутствующей отклоняются
      как `invalid_argument` до выбора провайдера и без dispatch.
- [x] Отсутствие режима отклоняется с указанием обоих допустимых флагов.
- [x] Неверный суффикс и нечитаемый вход отклоняются до dispatch.
- [x] `--dry-run` возвращает `provider_dispatched=false`, `restored=false`,
      `target_state=unchanged` и `plan` с провайдером, входом и режимом; процесс
      не запускается.
- [x] IBCMD-only окружение не диспетчеризует загрузку и показывает кандидата
      `experimental`.
- [x] DT-вход остаётся неизменным после загрузки.
- [x] Живая проверка на 8.3.27.2074: оба режима и превью; `/RestoreIB` headless,
      лог платформы — «Загрузка информационной базы успешно завершена».
- [x] Существующие parse/output snapshots `infobase` не изменились.
- [x] MCP tool list не изменился.

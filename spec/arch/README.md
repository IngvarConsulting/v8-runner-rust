# Нормативный слой

Три реестра. Одна запись — один файл. Символ и путь выводятся друг из друга.

| Каталог | Что лежит | Символ |
| --- | --- | --- |
| `decisions/` | что решено и почему | `DEC.<дата>.<ИМЯ>` |
| `invariants/` | правило, которое не должно молча сломаться | `INV.<ОБЛАСТЬ>.<ИМЯ>` |
| `contracts/` | форма наблюдаемого: провод, формат, конверт | `CTR.<ОБЛАСТЬ>.<ИМЯ>` |

[`index.md`](index.md) — одна строка на символ, порождается
`scripts/arch/registry.py --write-index`. Читайте его первым: полный текст нужен,
только когда символ уже выбран.

Модель реестра заимствована из проекта [Unica](https://github.com/IngvarConsulting/unica)
(`arch/`) вместе с правилами ниже.

## Индекс

Индекс и порождается, и коммитится, поэтому свежесть у него держит гейт:
`registry.py --check` сверяет файл с тем, что порождается из записей прямо сейчас, а
`tests/arch_registry.rs` зовёт тот же гейт.

Расходятся в индексе любые две ветки, заведшие по записи: строки отсортированы по
символу, и две новые строки встают в одно место. Разрешается такое всегда одинаково и
без выбора, поэтому разрешает git, а не человек. Файл драйвера называет
`.gitattributes`, а регистрируется драйвер в конфиге клона — один раз на клон:

```sh
python3 scripts/arch/registry.py --install-merge-driver
```

Драйвер сливает строки по символу: единица — строка, сторон три, порядок восстановлен
сортировкой. Перепородить индекс он не может: посреди слияния записей чужой стороны на
диске ещё нет, и порождение дало бы индекс без них — зато без конфликта, то есть
устаревший молча. Последнее слово поэтому за `--check`: собранное неверно слияние
останавливает гейт свежести.

Без регистрации git берёт обычное текстовое слияние и показывает конфликт — как и до
драйвера. Чинится он механически, выбор стороны ни на что не влияет:

```sh
git checkout --ours spec/arch/index.md
python3 scripts/arch/registry.py --write-index
git add spec/arch/index.md
```

## Как устроена запись

Файл открывается блоком полей между строками `---`, дальше идёт текст. Поля —
подмножество YAML: скаляр, плоский список, `null`. Запись, которой нужно больше,
переросла свой предмет.

Плоский список пишется двумя видами — потоковым `[a, b]` и блочным:

```yaml
check:
  - tests/cli_build.rs::build_dry_run_plans_every_source_set
  - tests/cli_convert.rs::convert_dry_run_plans_every_source_set
```

Вид записи на значение не влияет. Блочный есть потому, что `check` называет до пяти
адресов вида `путь::имя_теста`, и в одну строку это давало за четыреста знаков. Оба гейта —
`scripts/arch/registry.py --check` и `tests/arch_registry.rs` — читают оба вида
одинаково: этого требует `DEC.2026-09-16.FRONT-MATTER-HAS-ONE-READER`.

Имя файла решения — `<дата>-<имя>.md` строчными буквами, цифрами и дефисом; символ
решения — то же имя заглавными. У правила имя файла и есть символ. Префикс символа
называет каталог, так что по символу файл находится без индекса, а по файлу
восстанавливается символ.

Текст решения — заголовок, ровно один блок `**Решение.**` и не больше сорока
непустых строк. Длинное рассуждение живёт в `spec/design/`, план работ — в
`spec/IMPLEMENTATION_TODO.md`.

Запись говорит о своём предмете и не пересказывает смысл полей: он описан здесь.

## Поля

**У всех трёх видов.**

| Поле | Значения | Что значит |
| --- | --- | --- |
| `id` | символ записи | Совпадает с путём файла; по одному восстанавливается другое. |
| `status` | `active`, `planned`, `superseded` | `active` уже связывает дерево; `planned` принято как направление, но ещё не реализовано; `superseded` заменено преемником. У правила `planned` значит «принято, тест ещё не написан». |
| `governs` | `product`, `process` | Кто заметит нарушение: потребитель или только мы. |

**Только у решения.**

| Поле | Значения | Что значит |
| --- | --- | --- |
| `realized` | путь к свидетельству или `null` | Чем доказано соответствие дерева решению. Для `active` свидетельство обязательно, для `planned` равно `null`. |
| `supersedes` | список символов | Кого эта запись заменяет. |
| `superseded-by` | символ или `null` | Кто заменил эту. |
| `establishes` | список символов | Правила, выведенные из решения. |
| `changes` | непустой список символов правил | Наблюдаемую форму каких правил решение меняет. |

**Только у правила — инварианта и контракта.**

| Поле | Значения | Что значит |
| --- | --- | --- |
| `check` | адрес `путь::имя_теста`, список таких адресов или `null` | Что падает при нарушении. Имя обязательно: адрес файла с сотней тестов не называет фальсификатор. `null` допустим только при `status: planned` и означает, что тест ещё надо написать. |
| `decision` | непустой символ решения | На каком основании правило существует. |
| `scope` | непустой список из `cli`, `mcp`, `config`, `platform`, `use-cases`, `docs`, `ci`, `wire` | Область. Перечень открытый, дрейф виден в индексе. |

**Только у контракта.**

| Поле | Значения | Что значит |
| --- | --- | --- |
| `version` | положительное целое | Номер формы. Меняется, когда меняется сама форма. |
| `artifact` | путь к файлу | Чем форма закреплена: схема, снимок, фикстура. Проза формой не является; файл обязан существовать. |
| `producer` | путь | Что эту форму порождает. |
| `consumers` | непустой список из `cli`, `mcp`, `unica`, `ci`, `docs` | Кто на неё опирается. |

## Что чем отличается

**Инвариант против контракта.** У инварианта есть проверка и нет версии; у
контракта есть производитель, потребители, версия и закреплённая форма.

**Контракт без артефакта не заводится.** Форму фиксирует файл — схема, снимок или
фикстура, — а проверка сверяет с ним живой вывод производителя. Описание формы
словами обратную совместимость не удерживает.

**У контракта есть проверяемый пример.** Раздел «Пример» обязателен и содержит блок
кода. Если артефакт — схема, пример обязан её пройти целиком; если артефакт —
закреплённый документ, пример обязан быть его фрагментом. Схема отвечает на вопрос
«что допустимо», пример — «как это выглядит», и непроверяемый пример врёт с первой же
смены формы.

**Правило без проверки заводится и говорит об этом.** У него `status: planned` и
`check: null`; индекс показывает это колонкой «проверяется». Так долг виден и
считается, а не исчезает вместе с записью.

**Правило заявляет ровно то, что проверяет или будет проверять.** Одно правило —
одно утверждение и один фальсификатор. Утверждение, которому теста не будет,
правилом не становится и остаётся внутри решения.

**Намерение не называется действующим.** Пока направление не реализовано, решение
имеет `status: planned` и `realized: null`; правило без написанного теста — те же
`planned` и пустой `check`. Перевод в `active` идёт вместе с кодом и именованным
свидетельством.

**Атомарность.** Одна запись — один предмет. Решение, у которого в тексте
нумерованный список самостоятельных правил, разваливается на столько записей,
сколько в нём предметов: иначе его нельзя ни заменить по частям, ни сослаться на
одну его часть.

## Как менять

**Решение не правят.** Заводят преемника: у нового `supersedes`, у старого
`status: superseded` и `superseded-by`. Текст старого не редактируется никогда.

**Правило править можно** — вместе с решением, которое эту правку заводит и на
которое правило теперь ссылается.

**Правило убирают преемником.** Пока решение действует, названный им символ обязан
разрешаться в запись: удалить файл правила, оставив символ в `establishes`, нельзя.
Правило выводит из обращения преемник решения, и `establishes` заменённой записи
остаётся историей.

**Процессную запись правят свободно.** Её и заводят, чтобы перестроить в тот день,
когда разрабатывать стало неудобно.

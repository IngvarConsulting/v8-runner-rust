# ADR-0027: Состав расширений информационной базы

- Статус: `accepted`
- Дата: `2026-09-11`
- Связанные решения: [ADR-0001](0001-granitsy-podderzhki-ibcmd-kak-ogranichennogo-backend.md), [ADR-0005](0005-razdelit-cli-i-mcp-publichnye-poverhnosti.md), [ADR-0006](0006-sohranyat-transportno-neytralnyy-use-case-sloy.md), [ADR-0011](0011-eksklyuzivnoe-vladenie-workpath-na-vremya-komandy.md), [ADR-0022](0022-universalnyy-mehanizm-podgotovki-rasshireniy-i-client-mcp-extension.md)

## Контекст

Команда `extensions` до сих пор знала один предмет: свойства безопасности у
extension `source-set` рабочего пространства. Вопрос «какие расширения стоят в
этой информационной базе» раннером не отвечался вообще, а это другой предмет:
набор-расширение в проекте и расширение, подключённое к базе, связаны лишь по
смыслу.

Замер `ibcmd help extension` и `ibcmd help config extension` на 8.3.27.2074
показал, что платформа закрывает весь этот предмет пятью командами, и обе ветви
(`extension` и `config extension`) принимают один и тот же набор:

```text
create  --name --name-prefix [--synonym --purpose]
info    --name
list
update  --name [--active --safe-mode --security-profile-name
               --unsafe-action-protection --used-in-distributed-infobase --scope]
delete  --name | --all
```

Из них раннер пользовался ровно одной — `update` с двумя свойствами из шести.

**Вывод платформы измерен, а не выведен.** `list` на базе с двумя расширениями:

```text
name                         : "Вторая"
version                      :
active                       : yes
purpose                      : patch
safe-mode                    : yes
security-profile-name        :
unsafe-action-protection     : yes
used-in-distributed-infobase : no
scope                        : infobase
hash-sum                     : "HFmRgcnNuCfOYQLhjscUgqE7ZJI="
```

Четыре факта формы: записи разделены пустой строкой; ключ выровнен пробелами до
`: `; строки в кавычках, перечисления и булевы без них; незаданное поле пусто.
Машинного режима вывода нет. Пятый факт — **порядок не совпадает с порядком
создания** и платформой не документирован.

## Решение

Добавить к `extensions` подкоманды `list`, `info`, `create`, `delete`,
`activate`. Подкоманда необязательна: её отсутствие сохраняет опубликованное
поведение (правка свойств extension `source-set`), поэтому прежние вызовы не
ломаются.

**Выбор цели явный.** Подкоманды адресуют информационную базу, вызов без
селекторов — extension `source-set` рабочего пространства. `--name` по-прежнему
означает имя `source-set`; неизвестное имя отклоняется без перехода к поиску в ИБ.

Уточнение по #43: повторяемый `--installed-name` выбирает платформенное имя
установленного расширения для той же правки двух свойств безопасности. Совпадение
с `source-set` не требуется; валидный конфиг проекта по-прежнему нужен. Если задан
хотя бы один селектор, неявного выбора всех нет. При смешанном вызове сначала идут
явные `--name`, затем `--installed-name`; точные повторы итоговых имён выполняются
один раз, регистр и представление имени сохраняются. Пустые/пробельные имена,
управляющие символы и имена с начальным `-` отклоняются до lock и cleanup.
Селекторы родительской команды несовместимы с подкомандами.
Этот конфликт проверяет `ExtensionsArgs::validate_property_options` до загрузки
конфига и повторно на границе CLI dispatch. Общий запрет аргументов Clap здесь
не используется: он запрещал бы и допустимые глобальные `--json-message`/`--config`
перед подкомандой.

Разрешение целей остаётся у `configure_extensions::resolve_targets`, выполнение
— у существующего `configure_extensions::execute`. Предварительного чтения
состава нет: ошибка обновления, в том числе отсутствующего расширения, сохраняет
код платформы и квитанцию шага без классификации по тексту. MCP surface не меняется.

**Семейство IBCMD-only, и это названо.** У Designer батч-ключа, перечисляющего
установленные расширения, нет. Значит `builder` здесь ничего не выбирает, а
отсутствие `ibcmd` — отказ, а не переход на альтернативу. Словарь кандидатов
(`implementation`/`readiness`/`evidence`) не вводится: развилки нет, и
перечислять одного кандидата значило бы выдумать выбор.

**Разбор текста fail-closed.** Запись без обязательного поля и `yes/no`-поле с
иным значением отклоняются как `invalid_output`. Умолчание здесь хуже отказа:
вызывающий прочитал бы подставленное значение как наблюдение. Пустое поле
платформы — отсутствующее значение, а не пустая строка; в JSON оно отсутствует.

**`info --name` проверяет личность ответа.** Платформа отвечает на `info` той же
формой записи, что и `list`, поэтому без проверки ответ про другое расширение
ушёл бы вызывающему как запрошенный.

**Порядок не обещается.** Раз платформа его не документирует, раннер его не
объявляет, а перечисляет записи в том порядке, в котором их получил.

**`activate` отдельной подкомандой.** Платформа даёт активность самостоятельным
ключом, независимо от подключения, поэтому и раннер даёт её отдельным действием,
а не полем внутри обновления свойств.

**Чтение и запись делят границу workspace lock.** Состав может измениться под
чтением, и перечень, снятый поперёк установки, показал бы половинное состояние.

**`--dry-run` есть у обновления свойств и каждой подкоманды, включая читающие.** «Просто прочитать» не
бывает: поднимается `ibcmd`, открывается соединение, проходит аутентификация,
проверяются права, в журнале остаётся след. Значит чтение состава — действие, и
превью ему нужно ровно так же, как изменению. Превью называет **цель и учётку** —
то, что вызывающий должен знать до одобрения, — и утилиту, которая пойдёт:

```text
would read every installed extension of file infobase '/path/ib' as 'Админ' via /opt/1cv8/.../ibcmd
```

Секреты в это описание не попадают: сырая строка соединения может нести `Pwd=`,
поэтому она не воспроизводится, а называются только узнаваемые части цели.
В превью чтения `extensions` пуст — у платформы ничего не спрашивали, и пустой
список здесь значит «не спрашивали», что и отличает его от `provider_dispatched`.
Превью обновления свойств возвращает планируемые `steps` с
`provider_dispatched=false` после разрешения целей и поиска утилиты. Оно не
проверяет наличие расширения в ИБ, не запускает платформу, не берёт workspace lock
и не создаёт `workPath`; сочетание с `--clean-before-execution` отклоняется.
Как у превью `infobase`, родительское `extensions --dry-run` в `app.rs`
возвращается через существующий CLI dispatcher до инициализации action logging:
ни JSON-режим, ни debug-журнал не создают каталог логов при успехе или отказе.
Загрузка конфига для этого превью использует режим `Preview` существующего
`load_config_with_mode`: schema, overlay и нормализация путей общие.
`validate_project_checks` владеет общим списком семантических проверок проекта;
обычный `validate` сохраняет порядок base path → создание `workPath` → общие проверки,
а `validate_read_only` пропускает только создание каталога. Сокращённая валидация
экспорта ИБ здесь не используется.
До общих проверок превью проверяет структуру `workPath` во всех форматах, включая
DESIGNER: существующая цель должна быть каталогом, а отсутствующая — разрешаться
через допустимых предков без записи на диск. Проверяется канонический кандидат из
`nearest_existing_canonical_path`, включая существующие компоненты после `..`;
ошибки разрешения и доступа не скрываются. Возможность последующей записи и
права учётной записи в ИБ этим не доказываются.
Проверки пересечения EDT-исходников и generated targets (включая tool extension)
берут канонический `workPath` через существующий `nearest_existing_canonical_path`:
он разрешает symlink у существующего предка и добавляет ещё не созданный остаток.
Fallback к сырому пути недопустим: превью иначе пропускает пересечение через alias.
Общий helper поддерживает `..` в ещё не созданной части пути и разрешает существующие
компоненты после него, включая symlink: допустимый `scratch/../work` не должен
отвергаться превью только потому, что `scratch` ещё нет. Обход через обычный файл,
dangling link и ошибки доступа отклоняются; существующий путь по-прежнему
разрешается штатным `canonicalize`. Регрессии helper находятся в `support::path`.

**Reintroduction guard (#43).** Причина дефекта — смешение имени набора исходников
и имени установленного расширения при выборе цели. Единственный владелец выбора —
`configure_extensions::resolve_targets`; регрессии в `tests/cli_extensions.rs`
проверяют прямое имя без extension `source-set`, отсутствие неявного выбора всех,
отказ неизвестного `--name` до побочных эффектов и невозможность проигнорировать
селектор при вызове подкоманды.
Отдельный guard превью проверяет отсутствие даже пустого `workPath` при JSON/debug,
успехе и отказе, включая семантически некорректную конфигурацию: обход журналов сам
по себе недостаточен, поскольку прежняя полная валидация тоже создавала каталог.
Guard путей DESIGNER отклоняет файл вместо `workPath`, проход через файл и dangling
symlink без запуска платформы; допустимые отсутствующие каталоги и `..` остаются
разрешены. Guard конфликта `--dry-run` с очисткой проверяет не только сообщение:
нужны исходный `command`, `error.code=invalid_argument` и `error.kind=validation`.
Единственный владелец отказа — `with_cli_workspace_lock`, который использует общий
`render_pre_dispatch_error`; отдельного конверта для конфликта превью нет.

**Какое право нужно — раннер не называет.** Платформа требуемое право не
сообщает, и выдумывать его имя превью не станет; оно называет учётку, под которой
пойдёт, а право остаётся прозой вызывающего.

## Последствия

- Вопрос «какие расширения стоят в базе» получает дом в раннере; у Unica
  появляется чем закрыть семейство G своего словаря `run`.
- **Префикс имён на чтении недостижим.** Платформа не сообщает `name-prefix` ни
  в `list`, ни в `info`; он есть только в `Configuration.xml` расширения. Либо
  требование снимается, либо ответ на него — отдельное действие (выгрузка).
- `update` по-прежнему ставит два свойства из шести. Полный набор — отдельная
  задача: у него шесть ключей и своя форма отказа на каждый.
- Текстовый разбор привязан к формату 8.3.27. Смена формата вывода сломает
  разбор громко (`invalid_output`), а не тихо — это намеренный выбор.

## Верификация

- [x] Разбор замеренного вывода на двух расширениях даёт две записи со всеми
      полями; пустые `version` и `security-profile-name` отсутствуют, а не пусты.
- [x] Пустой вывод — пустой состав, а не отказ.
- [x] Запись без обязательного поля, небулево `yes/no`-поле и строка без ключа
      отклоняются.
- [x] `info --name` отклоняет ответ про другое расширение.
- [x] `list`, `create`, `delete`, `activate` доходят до своих команд платформы с
      точными ключами.
- [x] Голый `extensions` сохраняет прежнее поведение и прежний вывод.
- [x] Живая проверка на 8.3.27.2074: создание, перечень, снятие активности
      (отражается в `active: false`), удаление, отсутствующее расширение —
      ошибка платформы с её текстом.
- [x] MCP tool list не изменился.

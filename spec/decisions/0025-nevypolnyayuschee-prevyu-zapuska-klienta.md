# ADR-0025: Невыполняющее превью запуска клиента

- Статус: `accepted`
- Дата: `2026-09-11`
- Связанные решения: [ADR-0005](0005-razdelit-cli-i-mcp-publichnye-poverhnosti.md), [ADR-0006](0006-sohranyat-transportno-neytralnyy-use-case-sloy.md), [ADR-0008](0008-derzhat-platformennye-backend-dsl-otdelno-ot-orchestration.md), [ADR-0024](0024-tipizirovat-eksport-konfiguratsii-i-snimka-ib.md)

## Контекст

`infobase ... --dry-run` по ADR-0024 уже отвечает на вопрос «что именно сделает
команда», не делая этого. Для `launch` такого ответа нет: единственный способ
узнать, какой бинарник выберет runner и с какими аргументами он его запустит, —
запустить клиент.

Это мешает вызывающему orchestrator по трём причинам:

1. Платформу ищет только runner. `tools.platform.path` задаёт explicit-only
   границу, а `version` фильтрует поиск, поэтому вызывающая сторона не может
   воспроизвести выбор бинарника и тем более составить argv сама.
2. Отдельной команды discovery нет: `config` умеет только `init`.
3. Запуск клиента — наблюдаемое внешнее действие: открывается GUI, занимается
   сеанс ИБ. Пробный запуск «только чтобы посмотреть» не бесплатен.

При этом argv запуска содержит секреты: runner добавляет `/N <user>` и
`/P <password>` отдельными элементами, а сырая connection string может нести
`Pwd=`. Превью, печатающее argv дословно, превратило бы диагностику в утечку.

## Решение

Добавить `--dry-run` к `launch`. Превью проходит ту же валидацию запроса и тот
же поиск платформы, составляет тот же `ProcessRequest` и останавливается до
взятия runner-а и любого spawn.

```text
v8-runner launch <designer|thin|thick|ordinary> [--dry-run] [FLAGS]
```

Результат `launch` получает два поля:

```text
provider_dispatched: bool        // всегда присутствует
plan: { program, args } | absent // присутствует только у превью
```

`provider_dispatched` отвечает ровно на один вопрос — дошёл ли запуск до spawn
клиентского процесса, — и присутствует в обоих режимах, чтобы отсутствие поля
никогда не приходилось читать как «не запускали». У превью `ok=true`,
`pid=null`, `provider_dispatched=false` и заполненный `plan`.

`plan` называет выбранного провайдера, потому что его выбирает только runner;
`platform_resolution` остаётся прежним и описывает ту же установку подробнее.

В `plan.args` маскируются три независимых пути утечки, каждый своим правилом:
значение ключа `/P` (отдельным элементом и через `=`, `:`, пробел, кавычку),
сегмент `Pwd=` внутри connection string и известное значение
`infobase.password` где бы оно ни встретилось. Замена — `***`, как у
`bootstrap`. Остальные аргументы остаются читаемыми: превью нужно именно для
того, чтобы их прочитать.

`--dry-run` отклоняется вместе с `--wait-for-exit` и `--wait-ready`: оба
сообщают исход работающего клиента, которого превью не запускает, и ответ на них
планом был бы выдуманным наблюдением.

MCP surface не меняется: превью остаётся CLI-возможностью, как и у `infobase`.

**Уточнение 2026-09-14.** Маскирование секретов — общее правило всей поверхности, а не
свойство этого превью: пароли информационной базы и СУБД, значение `/P` и сегменты строки
подключения маскируются в превью, квитанциях и журналах, в текстовом и в JSON-виде. Здесь
оно реализовано первым; инвариант записан в разделе `Providers` файла
`spec/architecture/invariants.md`.

## Последствия

- Orchestrator может показать и проверить команду запуска до её выполнения, не
  повторяя у себя платформенный discovery.
- `provider_dispatched` появляется в JSON обычного `launch` как `true`; это
  additive-изменение контракта.
- Маскировка односторонняя: по превью нельзя восстановить пароль, поэтому argv
  из превью нельзя использовать как готовую команду для ручного запуска.

## План реализации

1. Добавить `dry_run` в `LaunchArgs`, `LaunchRequest` и CLI-отображение.
2. Добавить `provider_dispatched` и `LaunchPlan` в domain result.
3. Вернуть превью в `launch_app` после составления `ProcessRequest` и до spawn.
4. Добавить маскировку argv рядом с `build_launch_args`.
5. Обновить `README.md`, `docs/CAPABILITIES.md`, `SKILL/SKILL.md` и инварианты.

## Верификация

- [x] Превью не создаёт процесс: скрипт-заглушка платформы не пишет свой лог.
- [x] Превью возвращает `provider_dispatched=false`, `pid=null` и `plan` с
      выбранной программой и составленными аргументами.
- [x] Пароль ИБ не попадает в `plan.args` ни как значение `/P`, ни как сегмент
      `Pwd=`, ни как литерал; имя пользователя остаётся читаемым.
- [x] Ключи, лишь начинающиеся на `p` (`/Proxy`, `/PublishWSOnDemand`), не
      маскируются.
- [x] `--dry-run` с `--wait-ready` отклоняется до поиска платформы.
- [x] Обычный `launch` сохраняет прежний результат и получает
      `provider_dispatched=true`.
- [x] Живая проверка на 8.3.27.2074: текст и `--json-message` показывают план с
      замаскированными секретами, процесс `1cv8c` не появляется.

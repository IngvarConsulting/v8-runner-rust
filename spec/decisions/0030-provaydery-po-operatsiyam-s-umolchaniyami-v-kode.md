# ADR-0030: Провайдеры назначаются по операциям, умолчания живут в коде

- Статус: `accepted`
- Дата: `2026-09-13`
- Связанные решения: [ADR-0011](0011-eksklyuzivnoe-vladenie-workpath-na-vremya-komandy.md), [ADR-0017](0017-v8project-yaml-source-set-kak-glavnyy-konfiguratsionnyy-kontrakt.md), [ADR-0018](0018-perenesti-kontrakt-informatsionnoy-bazy-v-infobase.md), [ADR-0024](0024-tipizirovat-eksport-konfiguratsii-i-snimka-ib.md), [ADR-0028](0028-prevyu-u-glagolov-bez-vybora-provaydera.md) — уточняется в части квитанции, [ADR-0029](0029-proza-instrumenta-ne-prinimaet-resheniy.md)

## Контекст

`builder` — один ключ на весь `v8project.yaml` со значениями `DESIGNER` и `IBCMD`.
Матрица поддержки в `docs/CAPABILITIES.md` показывает, что он давно не описывает
реальность: `convert` его не использует, `infobase dump` знает только Designer,
`load` и `make` работают только при `builder=DESIGNER`, а экспорт трактует ключ
как «предпочтение, дальше выбираю сам». Выбор исполнителя пооперационный, а ключ
глобальный.

Замер 13.09.2026 на `8.3.27.2074` (подробности — задача
[#82](https://github.com/IngvarConsulting/v8-runner-rust/issues/82)) добавил
исполнителя, у которого набор команд не совпадает ни с одним из двух имеющихся, и
сделал противоречие жёстким:

1. **Агентский режим Конфигуратора и SSH-шлюз автономного сервера — один и тот же
   shell.** Баннеры разные, приглашения разные (`designer>` и `user@DefAlias>`), а
   `help config` совпадает побайтно: `dump-cfg`, `dump-config-to-files`, `load-cfg`,
   `load-config-from-files`, `generation-id`, `extensions …`, `manage-cfg-support`,
   `sign-cfg`, `update-db-cfg`, `dump-ib`, `restore-ib`. Для автономного сервера
   отдельный процесс Конфигуратора не нужен.
2. **Покрытие у этого shell'а своё.** В нём нет `check-config`, `CompareCfg`,
   `MergeCfg` — они остаются только у пакетного Конфигуратора. Зато есть
   `generation-id`, которого у пакетного Конфигуратора нет вовсе, и ответы приходят
   JSON-массивом с закрытым множеством `error-type` — то, чего ADR-0029 добивался от
   пакетного режима обходными путями.
3. **Аутентификация подчиняется правилу пакетного Конфигуратора.** База без
   пользователей: агент принимает пустой логин с пустым паролем, шлюз — любое имя с
   пустым паролем. База с пользователями: только пользователь ИБ и пароль.
   Пользователя «по умолчанию» нет. Значит `infobase.user` нужен агентскому
   исполнителю ровно тогда, когда он нужен `/N`.
4. **Готовность зависит от среды, а не от конфига.** `ibcmd --pid` отвечает через
   10–20 с после старта автономного сервера и не отвечает никогда при
   `--enable-extended-designer-features`; `ibcmd --pid config export` пишет ноль
   файлов и не завершается; `ibcmd --remote=ssh://` работает только с терминалом.
   Что из этого доступно, известно перед запуском, а не при чтении YAML.
5. **Есть исполнитель без платформы.** `ibcmd-rs` (Павел Чегодаев) конвертирует
   XML↔CF без Конфигуратора с байтовой точностью 98,9 % против родной выгрузки —
   пригоден для экспериментов и не пригоден для умолчаний.

Второй вход в решение — не платформа, а вызывающий. Раннером пользуется и человек,
и модель. Развилка «какой провайдер» на проводе означала бы, что модель начнёт её
исследовать: она не знает, какой из них лучше, и будет пробовать. Выбор исполнителя —
инженерное знание о платформе, оно принадлежит раннеру.

## Решение

**1. Три оси разделяются: операция, цель, провайдер.** Операция — глагол раннера
(`init`, `build`, `load`, `dump`, `make`, `extensions`, `infobase configuration
export`, `infobase dump`, `infobase restore`, `generation-id`, `syntax`). Цель —
вид информационной базы: файловая, кластерная, автономный сервер; выводится из
`infobase.connection` (`File=`, `Srvr=…;Ref=…`, `ws=`) и дополняющих секций.
Провайдер — способ исполнения:

| провайдер | что это |
| --- | --- |
| `designer-batch` | процесс Конфигуратора на операцию, как сегодня |
| `agent` | агентский shell по SSH; точку входа выбирает цель: для файловой и кластерной базы раннер поднимает `1cv8 DESIGNER /AgentMode`, для автономного сервера — шлюз работающего `ibsrv` |
| `ibcmd` | офлайн-форма (`ibcmd infobase …`) для файловой и серверной базы, онлайн-форма (`ibcmd --pid … config …`) для автономного сервера; это следствие цели, не выбор, поэтому имя одно |
| `ibcmd-rs` | конвертер XML↔CF без платформы и без цели |

Онлайн- и офлайн-формы `ibcmd` — разные режимы утилиты, а не одна команда с
разной целью: `--pid … infobase config …` отвергается платформой.

**2. Умолчания — данные в коде, назначенные нами.** Матрица
`(операция, вид цели) → цепочка провайдеров` живёт в `domain/capability.rs` и
версионируется с бинарником. Цепочка, а не один элемент: готовность зависит от
среды, и раннер сам уходит к следующему в нашем порядке. Умолчания на дату
решения:

| операция | цепочка | почему |
| --- | --- | --- |
| `init` | `ibcmd` → `designer-batch` | `ibcmd` покрывает и файловую, и серверную базу; результат проверяется `generation-id` |
| `build`, `load` | `agent` → `designer-batch` | один процесс на замок, `error-type` закрытым множеством |
| `dump` | `agent` → `designer-batch` | `ibcmd-rs` в умолчания не входит, пока 98,9 % не станут 100 % |
| `infobase configuration export` | `agent` → `ibcmd` → `designer-batch` | |
| `infobase dump`, `infobase restore` | `agent` → `designer-batch` | `ibcmd` для DT остаётся `experimental` (пункт 1 долга) |
| `extensions` | `agent` → `ibcmd` → `designer-batch` | |
| `generation-id` | `agent` → `ibcmd` | у пакетного Конфигуратора такой команды нет |
| `syntax`, сравнение, слияние | `designer-batch` | единственный провайдер |
| автономный сервер, любая операция | `agent` (= шлюз `ibsrv`); `ibcmd --pid` только для чтения | онлайн-экспорт сломан, extended-флаг запрещён |

Порядок в цепочке задаётся словом владельца проекта. Замер каждой строки делается и
записывается как `evidence` (`documented`, `argv_tested`, `live_verified`) — это
улика для читателя, а не ворота: страж на уровень улики не вешается, и решение об
умолчании замером не блокируется. Провайдер с `implementation: experimental` в
цепочку умолчаний не ставится.

**3. Переопределение — только в файле конфигурации, одно на операцию, строгое.**

```yaml
providers:
  dump: ibcmd-rs        # эксперимент
  build: designer-batch # запасной путь: агент в этой среде не работает
```

Скаляр, без списков. Если названный провайдер для операции не готов — типизированный
отказ с причиной, **без отката на умолчание**: эксперимент, молча вернувшийся к
умолчанию, ничего не измерил; запасной путь, назначенный потому что умолчание
сломано, не должен возвращаться к сломанному. Валидация отклоняет ключ для
операции, у которой на данной цели один провайдер (развилки нет — нечего
переопределять), и имя провайдера, не реализующего операцию. Ключ допустим и в
`v8project.yaml` (решение команды о своей среде), и в `v8project.local.yaml`
(личный эксперимент) — оба видны в diff.

**4. На проводе провайдера нет.** Ни у MCP-инструментов, ни у CLI-флагов, ни у
аргументов вызова — так же, как сегодня строка подключения не принимается
аргументом. `init --builder` снимается вместе с `builder`. Через `Bash` флаг был
бы доступен модели точно так же, как через MCP.

**5. `builder` снимается.** Не переименовывается и не остаётся синонимом: ключ
обещал глобальный выбор, которого нет. `format` остаётся — это формат исходников,
к провайдерам он не относится.

**6. Квитанция объясняет выбор, а не предлагает его.**

```json
"provider": {
  "selected": "designer-batch",
  "origin": "default",
  "skipped": [{"provider": "agent", "reason": "auth_failed"}]
}
```

`origin` — `default` или `override` с именем файла; `skipped` — кого по пути
пропустили и почему. Неиспользованные альтернативы не перечисляются: перечень и есть
приглашение выбирать. Это уточняет ADR-0028: тот запрещал **выдумывать** развилку,
которой нет, и запрет остаётся; с матрицей развилка появляется настоящая, но в
квитанцию она входит как объяснение принятого решения. Экспортный конверт
(`selection` + `candidates` по ADR-0024) приводится к этой же форме: у него, как и у
остальных, будет одна форма квитанции о провайдере.

**7. Сессия живёт столько, сколько замок.** Провайдер `agent` открывает сессию при
захвате `workPath` (ADR-0011) и закрывает при освобождении; вложенная оркестрация
(`build` = загрузка + `update-db-cfg`) идёт в одной сессии. Это второй экземпляр
образца `platform/edt_session`, а не новая архитектура: те же ключи
`auto-start`, `startup_timeout_ms`, `command_timeout_ms` в `tools.designer_agent`.

**8. Транспорт — SSH без псевдотерминала, ответы — по JSON.** Первая команда сессии —
`options set --show-prompt=no --output-format=json`; границы ответов определяются по
JSON-массивам, не по приглашению. Готовность `agent` — результат SSH-аутентификации с
настроенными учётными данными или пустой парой; это структурный сигнал, и он один для
файловой базы и автономного сервера. Клиент SSH — в процессе (`russh`), а не внешний
`ssh`: замеренный рецепт через `SSH_ASKPASS_REQUIRE=force` требует OpenSSH ≥ 8.4, чего
на Windows не гарантировано, а пустое имя пользователя внешний клиент принимает только
через `-l ''`.

Для локального агента SFTP не нужен — файлы кладутся на диск и читаются с диска.
Замерено 13.09.2026: все пути команд агент разрешает относительно
`<AgentBaseDir>/<каталог пользователя>`, где соответствие «пользователь → каталог»
он сам пишет в `<AgentBaseDir>/agentbasedir.json` (пустой логин → `0`); абсолютный
путь трактуется как относительный и укладывается под тот же каталог; `..` выходит
на уровень `AgentBaseDir`, но не выше. Шлюз `ibsrv` делает то же относительно
каталога `--users-data`, а в сообщении называет файл `local:///gate.cf`. Выгрузка
`dump-config-to-files` побайтно совпадает с `ibcmd infobase config export` той же
базы (128 файлов, `diff -rq` пуст). Поэтому раннер ставит `AgentBaseDir` (и
`--users-data` у собственного `ibsrv`) в `workPath` и читает результат по правилу
раскладки, а не тянет его по SFTP.

**9. Автономный сервер — вид цели, а не провайдер.** `infobase.connection: ws=…` плюс
секция `infobase.standalone` (шлюз, при необходимости pid и каталог данных) — по
образцу `infobase.dbms`. Если `ibsrv` поднимает раннер, он ставит `--ssh-host-key`, а
`--enable-extended-designer-features` по умолчанию не передаёт: в замеренной среде с
этим флагом сервер не достигал готовности для `ibcmd --pid`. Флаг включается для
операции, которой он нужен (экспорт мобильного приложения и клиента), и тогда
готовность `--pid` проверяется, а не предполагается; готовность устанавливается
успешным `ibcmd --pid config generation-id`. Это основано на одном замере, не на
свойстве платформы, и пересматривается новым замером.

## Что решение не делает

- Не создаёт пользователей ИБ: пакетного ключа у платформы нет, а обход через
  тонкий клиент с временным серверным модулем в раннер не зашивается. Замер показал,
  что для агента это и не нужно.
- Не использует `ibcmd --remote=ssh://`, пока он требует терминала и без него падает;
  это состояние платформы, не принцип.
- Не вводит `ibcmd-rs` в умолчания и не даёт ему цели.

## Reintroduction guard

- Root cause: один ключ описывал выбор, который на деле пооперационный, и каждая
  новая операция либо игнорировала его, либо перетолковывала.
- Single owner: `domain/capability.rs` — матрица и цепочки умолчаний. Таблица в
  `docs/CAPABILITIES.md` сверяется с матрицей тестом, а не пишется отдельно.
- Detection: тесты валидации на три правила пункта 3 (ключ без развилки, провайдер
  вне матрицы, отказ без отката); тест на отсутствие `provider` среди аргументов MCP
  и CLI; `tests/tool_output_contract.rs` признаёт агентский JSON структурным
  контрактом, и решения по `error-type` в него не попадают.

## Последствия

1. Снятие `builder` затрагивает 31 файл — это и есть объём удаления; идёт вместе с
   появлением `providers`, чтобы у конфига не было двух ключей об одном.
2. `docs/CONFIGURATION.md`, `docs/CAPABILITIES.md`, обе JSON-схемы, `config init`,
   `bootstrap` синхронизируются по чеклисту при реализации; в Unica перестают
   писать `builder: DESIGNER` два рецепта (`epf-init`, `erf-init`).
3. Долг в `spec/IMPLEMENTATION_TODO.md`: матрица и `providers`; сессия `agent`;
   цель «автономный сервер». Порядок такой: сначала матрица и снятие `builder`
   (поведение не меняется, умолчания повторяют сегодняшний выбор), затем `agent`,
   затем автономный сервер.
4. Замечание Unica о двух валидаторах превью (следствие ADR-0028) пересматривается:
   с единой формой квитанции о провайдере у экспортного и запускного семейств один
   конверт.
5. Задача [#99](https://github.com/IngvarConsulting/v8-runner-rust/issues/99)
   (спросить платформу, изменилась ли конфигурация) получает дешёвый ответ:
   `generation-id` по сессии — около секунды вместо запуска Конфигуратора.
